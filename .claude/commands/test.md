`test-designer` サブエージェント（sonnet）を起動し、`docs/03_detailed-design.md` から
テストを書かせる。**実装より先に行う。**

## なぜ実装より先か

実装と同じモデルにテストを書かせると、テストは「仕様通りか」ではなく
「実装した通りか」を検証してしまい、バグを追認する。

先にテストがあれば、`/impl` で Codex に渡す仕事が
**「既にあるテストを通す」**という機械的な作業になり、成功率も上がる。

## 前提条件

`docs/03_detailed-design.md` に関数シグネチャと期待される挙動が書けていること。

## エージェント起動後にやること

1. **テストが落ちることを確認する。** 実装がないので落ちるのが正しい。

   ```bash
   npm test
   ```

2. 書かれたテストを読み、**設計の意図と合っているか**を検証する。
   sonnet は設計の曖昧な部分を推測で埋めることがある。期待値の根拠が
   `docs/03` にないテストは、テストではなく設計を疑う。

3. エージェントが「設計が曖昧で書けない」と報告した箇所は、
   **`docs/03` を直す。** 実装前に設計の穴が見つかったということなので、
   ここで直すのが最も安い。

4. **`tests/scenario/` を重点的に見る。** ここがこのプロジェクトの結合テストの本体で、
   3日の範囲でこれ以上の結合テストは行わない方針（`docs/04_test-plan.md`）。
   次の2点を必ず確認する。

   - **ターン数の上限があるか。** ないと、あいこが無限に続くバグを検出できず、
     テストがハングする
   - **途中経過の数値を検証していないか。** 「3ターン目に HP が 12」のようなテストは、
     `src/data/` を触るたびに壊れてバランス調整ができなくなる。
     検証は**決着時の状態**に限る

5. `docs/04_test-plan.md` の「これから書く」を実際の一覧に更新する。

## 守ること

- **テストを通すために `src/` を書かない。** それは `/impl` の仕事。
- テストが厳しすぎて実装が不可能になっていないかだけ確認する。
- **シナリオテストの失敗は Codex に丸投げしない。** 原因の層（`domain` か `application` か）を
  自分で特定してから、修正対象を名指しで渡す。
