# 調査: グリコ（じゃんけん階段）RPG の周辺調査

> ステータス: 調査中の前提を反映した最新版。
>
> **この調査は「戦闘」を前提にしない。** 作りたいのは「グリコ（じゃんけん階段）をしながら
> 進んでいくRPG」であり、じゃんけんの勝敗は**ダメージではなく進む歩数**に変換される。
> 戦闘を持つかどうか自体が、この調査が並べるべき論点の1つ。
>
> `docs/00b_research-battle.md` は「勝敗をダメージに変換する」前提の旧調査であり、
> 別前提のため触っていない。道中に戦闘フェーズを別立てで持つ構成（本調査の案4）を選んだ場合、
> `00b` の5案がそのまま使える資産として残る。
>
> 通信対戦は行わない。対戦相手は常に CPU。マルチプレイ・オンライン対戦は対象外。

## 1. グリコ（じゃんけん階段）のルールを正確に押さえる

**WebSearch で複数ソースを突き合わせて確認した。**

### 歩数と掛け声

| 手 | 掛け声 | 音数（＝歩数） |
| --- | --- | --- |
| グー | 「グ・リ・コ」 | **3歩** |
| チョキ | 「チ・ヨ・コ・レ・イ・ト」 | **6歩** |
| パー | 「パ・イ・ナ・ツ・プ・ル」 | **6歩** |

Wikipedia・デイリーポータルZ・45mix.net の3ソースが揃って「グー3・チョキ6・パー6」で一致した。
これは**掛け声の音数（モーラ数）＝歩数**という設計になっている（グリコ=3音、チヨコレイト=6音、
パイナツプル=6音）ため、恣意的な数値ではなく言葉遊びから逆算された数字だとわかる。
「パイナップル／パイナツプル」は促音の表記揺れであり、歩数に影響しない。

なお、じゃんけんのゲーム理論を扱った Qiita 記事は歩数を「グー3・チョキ5・パー6」という
別の数値で計算していた。これは「チョコレート」を「ちょこれーと」（長音を1音として5音）と
数えるローカルな流儀の可能性が高く、**標準ルールとしては3・6・6を採用する**（本調査の
期待値計算もすべて3・6・6で行う）。

### あいこ・負けた側の扱い

- **負けた側は進まない。** 勝った側だけが該当の掛け声を唱えながら進む（Wikipedia）。
  「負けたら後退する」というペナルティは標準ルールには存在しない。
- **あいこの扱いは資料によって明確でない。** 標準的には「あいこの間は誰も進まず、
  じゃんけんをやり直す」と考えられるが、地域によっては**あいこでも両者が進むローカルルール**
  （「あいこさま」5歩、「アイスクリイム」7歩など）が存在する（Weblio 辞書経由の要約）。
  つまり「あいこ＝停滞」は絶対のルールではなく、**決めてよい選択の1つ**。

### ゴール条件

- 決まった段数・マス数の階段やコースの**頂上（ゴール地点）に最初に到達した者が勝者**。
  相手より先にゴールする**相対競争**が本来の形。

### 地域差・ローカルルール

- グーの呼び方に地域差が大きい: 「グスベリ」（北海道）、「グリコス」（宮城県）、
  「グリコのおまけ」（千葉県ほか）など。
- 中には「グリコのオマケ（7歩）」「グリコのオマケつき（9歩）」のように、
  **グーの歩数だけを底上げする亜種**が存在する。これは後述するグーの弱さ（節2）を
  現場の子どもたちが体感的に把握し、house rule で補正してきたことの傍証と読める。
- パーの呼び方にも差がある（「パラシュート」＝北九州市周辺、など）。
- 階段でなく床のマス目やその場でのグーパー移動で遊ぶ地域もある（栃木県・広島県など）。

Sources:

- [じゃんけんの「グリコ」、グーが弱い気がするのでルールを再考する :: デイリーポータルZ](https://dailyportalz.jp/kiji/Janken_glico-rethinking-rules)

## 2. 歩数の非対称が生む読み合いの構造【最重要】

### 2.1 なぜ非対称だと読み合いが生まれるのか

3すくみが等距離（勝てば必ず1歩、のような対称ルール）なら、相手がどんな確率でグー/チョキ/パーを
出そうと、自分がどの手を出しても勝率は常に1/3。**手を選ぶことに意味がなくなる。**
歩数が手ごとに違うことで初めて、「同じ1/3の勝率でも、どの手で勝つかによって得られる価値が違う」
という差が生まれ、「相手の手を読んで、価値の高い勝ち方を狙う／安い手で相手の高い手を潰す」という
判断が発生する。これがグリコの戦略性の核。

### 2.2 期待値計算1: 相手が完全ランダム（各1/3）のとき

自分がある手 X を出したとき勝てるのは、相手が X に負ける1手を出したときだけ＝確率1/3。
勝ったときの歩数は X 自身の歩数（グー勝ち=3、チョキ勝ち=6、パー勝ち=6）なので、

```
EV(グー) = 1/3 × 3 = 1.0
EV(チョキ) = 1/3 × 6 = 2.0
EV(パー)  = 1/3 × 6 = 2.0
```

**相手がランダムなら、グーは損な手、チョキとパーは互角に得な手。** 「グーは弱い」という
体感（デイリーポータルZの記事タイトルもこれ）は、この単純な期待値計算で裏付けられる。
均等な相手を仮定する限り、グーを出す理由がなくなる。

### 2.3 期待値計算2: 双方が最適に読み合う場合（ミニマックス均衡）

しかし「グーを出さない」が最適なら、相手もそれを見越してグーを避け、
チョキとパーだけで打ち合うようになる。するとチョキとパーの間で今度は
「相手がチョキを避けるならパーが得、パーを避けるならチョキが得」という循環が起き、
結局グーにも出番が戻ってくる。この行き来が収束する点（ナッシュ均衡）を求める。

3すくみ（グーはチョキに勝ち、チョキはパーに勝ち、パーはグーに勝つ）で、
勝ったときの歩数を w_グー=3、w_チョキ=6、w_パー=6 として、相手が各手をどの確率で
出しても自分の期待利得が変わらない（＝つけ込む隙がない）比率を解くと、

```
グー : チョキ : パー = 0.4 : 0.4 : 0.2
（＝ 2 : 2 : 1）
```

になる（相対的な進み幅の差を利得とした零和ゲームとして、３本の無差別方程式を連立して解いた。
このとき期待利得はどちらのプレイヤーも0＝理論上は五分五分のフェアなゲームになる）。

**この結果は直感に反する。** 節2.2の「相手が均等ならグーは損」という単純な計算からは
「グーは避けるべき手」に見えるが、双方が読み合いを尽くした均衡では**グーはチョキと
同じ40%出す**のが正しい。理由は、グーの歩数が小さくても、グーは**歩数が大きいチョキを
安く潰せる保険**として機能するから。相手がチョキを打ちやすくなるほど、グーを混ぜて
「チョキの乱用」を罰する必要が生まれる。

さらに一般化すると、**均衡での出現頻度は「自分の勝ち歩数」ではなく「自分が倒す相手の
勝ち歩数」に比例する**という規則が見える。

- グーの頻度 ∝ チョキの歩数（6）— グーが潰す相手はチョキ
- チョキの頻度 ∝ パーの歩数（6）— チョキが潰す相手はパー
- パーの頻度 ∝ グーの歩数（3）— パーが潰す相手はグー

パーはチョキと並んで最大歩数（6）を持つのに、均衡での出現率は最も低い（20%）。
これは「パーが潰す相手＝グーの歩数が小さく、グーの乱用を警戒する必要が薄いから」
と説明できる。**歩数が大きい手ほど得、とは単純に言えない**のがこのゲームの面白さ。

### 2.4 実際に偏りが出るか、均衡するか

- **理論上の均衡**（節2.3）は五分五分でフェア。ただし均衡はあくまで「最適に打ち続けたときに
  収束する点」であり、実際の人間のプレイがそこに乗るとは限らない。
- **人間は単純な期待値（節2.2）で判断しがち**なので、実プレイでは**グーを過小に選びがち**
  という体感がデイリーポータルZの記事で報告されている。理論上はグーも40%出すべきなのに、
  「グーは損」という直感だけで避けてしまうバイアスが人間には残る。
- CPU 側がこのバイアス（グー回避）を学習・利用できれば、"人間らしい偏り"を突く形で
  読み合いを成立させられる（節4で詳述）。
- さらに `nabenavi.net`（グリコじゃんけんのゲーム理論的解析）によれば、**最適戦略は
  ゴールまでの残り距離によって動的に変わる**。ゴールに近いプレイヤーは、相手が
  一気に大きく進んで逆転するのを防ぐため、歩数の大きいチョキを出す確率を上げるべき
  だという分析結果が示されている。逆に両者ともゴールから十分離れている（あと3ステップ以上）
  状況では、通常の3すくみと同じ1/3ずつの均衡に近づくという。
  **つまり「最適な手の比率」は固定値ではなく、残り距離という状態に応じて動く。**
  これは終盤ほど緊張感が高まる構造がグリコに元から備わっていることを意味する。

### 2.5 非対称を強めたり弱めたりするとどうなるか

- **非対称を強める**（例: グー1歩・チョキ8歩・パー8歩）→ グーの「保険としての価値」が
  相対的に増し、均衡はよりグー寄りに偏る一方、1回の勝敗の重みが増すため**逆転・番狂わせが
  起きやすくなり、運の影響を体感しやすくなる**（大きく動く分、外した時の落差も大きい）。
- **非対称を弱める**（例: グー4歩・チョキ5歩・パー5歩）→ 通常のじゃんけんに近づき、
  均衡比率も1/3に近づく。読み合いの旨味は減るが、**進行スピードが安定し、テンポの
  予測がしやすくなる**（バランス調整・テストの両面で扱いやすい）。
- 完全対称（全部同じ歩数）にすると、節2.1の通り手を選ぶ理由自体が消える。
  **非対称であること自体がグリコというゲームの必要条件。**

## 3. 「進む」をRPGにする方式の案（5案）

1案に絞らない。各案は独立した設計であり、`domain/` に必要な状態の増え方でコストを見積もる。

---

### 案1: 純粋競争型（1体のCPUと並走レース、道中イベントなし）

グリコをほぼそのまま実装し、育成要素を歩数と敵の個性に乗せる、最も素直な案。

**1プレイの流れ（具体例）**: ゴール60歩のコースで、プレイヤーと敵CPUが同じ0地点から開始。
1ターン目、プレイヤーがパー、CPUがグーを出し、プレイヤー勝利でプレイヤー0→6。
2ターン目、プレイヤーがグー、CPUがパーで、CPUが0→6。3ターン目あいこ（双方チョキ）、
どちらも停滞。……これを繰り返し、先に60に到達した側が勝ち。

**RPGとしての伸びしろ**: 「レベルアップで何が変わるか」＝**歩数テーブルが強化される**
（例: グーで勝ったときの歩数+1）、または装備で「特定の手だけ歩数が増える」形にできる。
一言で言い切れる伸びしろがあり、節2の期待値計算とも直結する（強化された手ほど均衡比率が
変わる、という設計上の面白さも作れる）。敵の個性は「手の出現バイアス」（節4）で表現。

**実装コスト**: 最も軽い。

```ts
interface RaceState {
  playerPos: number;
  enemyPos: number;
  goal: number;
  turnCount: number;
  history: { player: Hand; enemy: Hand; result: 'win' | 'lose' | 'draw' }[];
}

function decideEnemyHand(state: RaceState, rng: Rng): Hand;
function resolveStep(state: RaceState, playerHand: Hand, rng: Rng): RaceState;
function isFinished(state: RaceState): 'player' | 'enemy' | null;
```

乱数は `decideEnemyHand` の1箇所のみ（重み付き `rng.pick` 等）。フィールドは4〜5個で済み、
`tests/scenario/` の「勝つまでの1試合」「負けるまでの1試合」「あいこ連続でも進行」の
3本もそのまま当てはめやすい。

**運ゲーになりにくさ**: 敵の手の出現バイアスを `history` からプレイヤーが読む。
節2の期待値計算がそのまま生きるため、「なぜその手を選ぶと得か」を理屈で説明できる
数少ない案。ただし1体との一本勝負なので、読みを外した瞬間の巻き返しが難しい
（挽回の手段が歩数ボーナス頼みになりがち）。

**相性の悪い点**: 敵1体・イベントなしのため、ステージを跨いでも同じ読み合いの
繰り返しになりやすく、探索・発見の楽しさが薄い。RPGとしての世界の広がりは出にくい。

### 案2: 一本道・関門突破型（複数の敵を順番に抜けるガントレット）

道中にイベントは置かず、一本道の上に「関門」となる敵キャラを複数並べ、
1体ずつグリコで抜いていく。並走ではなく、各関門ごとに固有の突破距離を設定する。

**1プレイの流れ（具体例）**: 第1関門「木こりの敵」は突破に必要な距離20、
プレイヤーの挑戦回数（ライフ）は3。1ターン目、プレイヤーがチョキ、敵がパーで勝利し
進捗0→6。2ターン目、敵の勝率が高いグー系の癖を読んでパーを選ぶが外れ、あいこで停滞。
3ターン目、チョキで再度勝利し進捗12。……20に到達したら関門突破、次の関門へ進み、
挑戦回数はリセットされずに引き継がれる。3回連続で負けが込むとライフが尽きて失敗。

**RPGとしての伸びしろ**: レベルアップで何が変わるか＝**ライフ（挑戦回数）の上限が増える**、
または「1勝あたりの歩数ボーナス」。関門ごとに敵の得意な手を `src/data/` に持たせれば
「このボスはグー壁」のような個性を出しやすい。装備・スキルは「特定の関門の癖を見抜く
ヒントを表示する」形で乗せられる。

**実装コスト**: 案1よりやや増える（ステージ管理・関門ごとのプロファイルテーブルが増える）が、
HP管理を伴う戦闘案より軽い。

```ts
interface GateState {
  gateIndex: number;
  progress: number;      // 現在の関門内での進み
  gateDistance: number;  // この関門の突破に必要な距離
  life: number;          // 残り挑戦回数
  turnCount: number;
}

function decideGateEnemyHand(state: GateState, rng: Rng): Hand; // gateIndex に応じたプロファイル参照
function resolveGateStep(state: GateState, playerHand: Hand, rng: Rng): GateState;
function isGateCleared(state: GateState): boolean;
```

乱数は敵の手決定の1箇所。ステージ（関門）が増えるごとに `src/data/gates.ts` の
テーブル行が増えるだけで、ロジック自体は増えない。

**運ゲーになりにくさ**: 関門ごとに固有の手の偏りを事前情報（図鑑・見た目）として出せるので、
「初見の関門は手探り、2周目は対策できる」という上達の余地がある。ライフという有限リソースが
逼迫感を生み、「安全に負けを引き延ばす」判断が意味を持つ（カイジ的な資源管理に近い緊張感）。

**相性の悪い点**: 分岐がなく一本道なので、周回時のバリエーションが単調になりやすい。
ライフ制を入れないと緊張感が出ない＝結局「負けの条件を別途設計する」作業が発生する。

### 案3: 分岐マップ＋道中イベント型

ボード上に分岐を持たせ、止まったマスに応じて宝箱・罠・ショップ・ミニ戦闘などの
イベントが起きる、最もRPGらしい探索型の案。

**1プレイの流れ（具体例）**: 現在ノードから分岐が2方向（安全ルート／近道だが罠が多いルート）。
プレイヤーは近道ルートを選択。じゃんけんでチョキを出し勝利、6マス進んで「宝箱マス」に停止し
アイテムを1つ入手。次のターン、あいこが続いて足止めされている間に、罠マスを踏み
「2歩後退」のイベントが発動。……最終的に分岐が合流するゴールノードに到達したらクリア。

**RPGとしての伸びしろ**: レベルアップで何が変わるか＝**イベントの当たりの質が上がる**
（宝箱の中身が良くなる、罠を無視できる確率が上がる等）。5案の中で装備・スキル・アイテムの
乗せ場所が最も豊富で、探索型RPGらしい厚みを一番出しやすい。

**実装コスト**: 5案中もっとも重い部類。

```ts
interface BoardState {
  nodes: BoardNode[];      // グラフ構造 or 固定配列
  currentNodeId: string;
  visited: string[];
  items: Item[];
  turnCount: number;
}

function resolveJankenStep(state: BoardState, playerHand: Hand, rng: Rng): BoardState;
function choosePath(state: BoardState, nextNodeId: string): BoardState;
function triggerEvent(state: BoardState, rng: Rng): BoardState; // マス種別に応じた抽選
```

乱数が「敵の手」「イベント抽選」の少なくとも2系統に分かれ、案4（戦闘を持たせる場合）と
組み合わせるとさらに増える。マップ構造・イベントテーブルの設計自体にも時間がかかる。

**運ゲーになりにくさ**: 「どちらのルートを進むか」という選択自体がじゃんけんの運と独立した
意思決定になり、プレイヤーの判断が結果に直接効く点は5案中最も強い。ただしイベント抽選という
新しい乱数が加わるため、じゃんけんの運＋イベントの運の**二重運ゲー**になる危険がある。

**相性の悪い点**: 3日規模では「マップ生成＋イベントテーブル＋じゃんけん」を同時に作ることになり、
最もスコープが膨らみやすい。`docs/04_test-plan.md` の「`tests/scenario/` は3本まで」という
方針とも相性が悪い。分岐が多いほど「決着時の状態」を一意に定義しづらく、シナリオテストで
何を検証対象にするかがぼやける。

### 案4: 移動フェーズ＋別立て戦闘フェーズのハイブリッド型

グリコによる移動フェーズと、`docs/00b_research-battle.md` が挙げた戦闘方式のどれかを
別フェーズとして組み合わせる。「戦闘を持つ」を選んだ場合の代表案。

**1プレイの流れ（具体例）**: 道中はグリコで進む（案1相当）。20歩地点で敵と接触すると
戦闘フェーズに切り替わり、`00b` の案2（手固有スキル型）のようなじゃんけん戦闘を行う。
戦闘に勝つと移動フェーズに復帰し、そのまま20歩地点から続きを進む。

**RPGとしての伸びしろ**: 移動と戦闘の両方に育成が乗る、最も贅沢な形。ただし
「レベルアップで何が変わるか」を一言で言うのが難しくなる（移動用ステータスと
戦闘用ステータスを両方管理することになるため）。

**実装コスト**: 5案中最も重い。移動フェーズ（案1相当）と戦闘フェーズ（`00b` の各案）を
両方作ることになり、フェーズ遷移の状態管理・UI もその分増える。

```ts
type Phase = 'move' | 'battle';
interface HybridState {
  move: RaceState;      // 案1のフィールド一式
  battle: BattleState | null; // 00b の案に準じる
  phase: Phase;
}

function enterBattle(state: HybridState, rng: Rng): HybridState;
function resolveBattleTurn(state: HybridState, playerHand: Hand, rng: Rng): HybridState;
function exitBattle(state: HybridState): HybridState;
```

**運ゲーになりにくさ**: 移動フェーズは節2の非対称読み合いが、戦闘フェーズは `00b` で
論じた各案の対策がそれぞれ効く。二重に対策できる反面、じゃんけんの運も二重に乗る。

**相性の悪い点**: 実装量がほぼ2倍になるため、3日には最も収まりにくい。**同じ「じゃんけん」
という入力が、移動中は歩数、戦闘中はダメージという別の意味を持つ**ため、プレイヤーが
混乱しやすい。「じゃんけんRPG」としてのアイデンティティが分裂するリスクがある。

---

### 案5: スコアアタック／周回進行型（エンドレス一本道＋メタ成長）

負け＝即終了ではなく、力尽きた地点までの到達距離をスコアとして記録し、
そのスコアで得た報酬を次の挑戦に永続的に持ち越す、ローグライク寄りの案。

**1プレイの流れ（具体例）**: シード42でラン開始。プレイヤーは一本道を延々グリコで進み、
一定間隔でCPUの個性が切り替わる（序盤はグー偏重の敵、中盤はチョキ偏重、など）。
連続で負けると「疲労ゲージ」が溜まり、上限に達すると力尽きてラン終了。
到達62歩がスコアとして記録され、獲得コインで「グーの歩数を永続+1」のような
メタ強化を購入し、次のランに引き継ぐ。

**RPGとしての伸びしろ**: レベルアップ（＝メタ成長）で何が変わるか＝**ランを跨いで
歩数テーブルや疲労上限が永続的に強くなる**。一言で言い切れる。

**実装コスト**: 単発ロジック自体は案1と大差なく軽いが、**ラン終了時の集計とメタ強化の
永続化**が別途必要になる（`localStorage` 等への保存は `application`/`ui` 側の仕事だが、
「メタ強化適用後のテーブルを計算する」関数は `domain` 側にも要る）。

```ts
interface RunState {
  position: number;
  fatigue: number;      // 連続敗北カウンタ
  turnCount: number;
}
interface MetaState {
  permanentUpgrades: UpgradeId[];
}

function resolveRunStep(state: RunState, playerHand: Hand, rng: Rng): RunState;
function isRunOver(state: RunState): boolean;
function settleRun(state: RunState): { score: number; rewardCoins: number };
function applyMetaUpgrade(meta: MetaState, upgrade: UpgradeId): MetaState;
```

**運ゲーになりにくさ**: 1回の負けが即終了せず「疲労」という緩衝を挟めるため、
単発の運の悪さがそのまま結果を決めない。メタ成長により実力不足を回数でも補えるので、
初心者でも進捗が積み上がり、運ゲー感が薄まる。

**相性の悪い点**: 「グリコ」という素朴な子どもの遊びに対し、コイン課金的なメタ成長は
世界観が乖離しやすい。3日で永続保存の仕組みまで作り込むと工数を食う。明確なゴールが
存在しないため、「クリアした」という達成感を求めるプレイヤーには物足りない可能性がある。

## 4. 1人プレイ（対CPU）で成立させるための論点

グリコは本来、掛け声のタイミングやその場の空気を読み合う**対人の心理戦**。
CPUに置き換えると失われるものと、それを補う方法を整理する。

### 何が失われるか

- 掛け声の「間」で相手の顔色・仕草を読む駆け引き（対人ならではの直感的読み合い）。
- 相手が自分の癖を学習してくる怖さ・悔しさという**対人特有の感情**。
- 「その場限りの一発勝負」という緊張感（CPUは何度でもリセットして再戦できてしまう）。

### 何で補うか

- 掛け声・アニメーションで疑似的な「間」を演出する（同時出しのタイミングを揃える）。
- CPUに**明示的な癖**を持たせ、図鑑や戦闘中の履歴グラフとして開示し、
  「相手の手グセを読んで対策する」という学習の快感で代替する。
- 敵キャラごとに強い個性（口調・見た目・得意な手）を持たせ、キャラ性で対人らしい
  緊張感を演出する。

### 読み合いが成立するCPUの作り方（複数案）

| 方式 | 内容 | 実装コスト |
| --- | --- | --- |
| a. 固定バイアス型 | 敵ごとにグー/チョキ/パーの出現確率を `src/data/` に固定（例: 55/25/20）。図鑑や履歴からプレイヤーが読んで対策する | 最も軽い。重み付き `rng.pick` 1箇所 |
| b. 直前結果依存型（1次マルコフ） | 「直前に勝った手を続けやすい」「直前に負けた手を避けやすい」など、直前の勝敗で確率テーブルを切り替える | 軽い。状態1つ（直前の手/結果）を持つだけ |
| c. 対プレイヤー履歴反応型 | プレイヤーの直近N手の頻度を集計し、それを最も崩す手を高確率で選ぶ。学術研究（後述）でも有効性が実証されている | b よりやや重い。直近履歴の保持と集計ロジックが要る |
| d. 均衡寄せ型 | 節2.3で導出した理論的均衡比率（2:2:1）に敵ごとの補正を掛ける | 軽いが、プレイヤーからは「読みにくい」＝学習で崩す隙がなく感じられ、体感がただのランダムに寄るリスクがある |

Rock-Paper-Scissors の学術研究（Nature Scientific Reports, 2020）では、直近の手の並びから
次の一手を予測する**マルコフモデル**を使った AI が、300戦ずつ対戦した52人の人間相手に
95%以上の勝率を叩き出したと報告されている。人間は短期的なパターンに陥りやすく、
それを突く AI は非常に強くなりやすい、という点は**そのまま「強すぎる境界」の警告**でもある。

### CPU が強すぎる／賢すぎると理不尽になる境界

- **絶対禁止**: 同じラウンド内でプレイヤーの入力を見てから手を決める「後出し」。
  これは学習でも読み合いでもなく、単なる不正に見える。
- 予測に使う履歴の窓（c方式のN）を長くしすぎない。学術研究の95%勝率のような精度は、
  ゲームとしては理不尽に近い。数手だけを見る・追従を緩めるなど、意図的に精度を落とす。
- 均衡（d方式）に完全に乗せたCPUは理論上最強だが、プレイヤーから見ると崩す手掛かりが
  なく「運ゲーにしか見えない」という別の問題を生む。**理論最適＝良い体験、ではない。**
- 一定確率でランダム行動を混ぜ、CPUの手にも「読み外し」の余地を残す。
  CPUが完全に読み切ってくると、プレイヤーの工夫が意味を失う。

## 5. 決着まわりで決めないと詰むこと

### あいこの扱い

標準ルールは「あいこの間は両者停滞、やり直し」（節1）。この方式のままだと理論上は
無限にあいこが続きうるため、`docs/04_test-plan.md` のシナリオ3
「あいこが連続しても進行する（無限ループにならない）」を満たすには**ターン数上限が必須**。

代替として、ローカルルールの「あいこさま」（あいこでも両者が固定歩数だけ進む）を採用すれば、
決着が自然に早まり無限ループの懸念自体が薄れる。ただしこの場合、じゃんけんの勝敗と無関係に
進行が発生するため、**「勝敗を読む」ことの意義がその分だけ薄まる**トレードオフがある。

### ゴール条件

- **相対競争型**（グリコ本来の形）: 相手より先にゴールした方が勝ち。CPUとの距離が
  近いほど緊張感が出るが、相手の位置を常に把握・表示する必要がある。
- **絶対距離型**（タイムアタック寄り）: 決められた距離やターン数以内にどこまで進めたかを
  スコアとして扱う。「相手に勝つ」ではなく「自己ベストを更新する」形になり、
  対CPU特有の「本当にこのCPUは公平に強いのか」という疑いを持たずに済む利点がある。

### 負けの条件

グリコ本来には「負け」という概念が薄い（先着でなければ、ただの2着）。RPGとして緊張感を
作るには、次のいずれかを決める必要がある。

1. 相対競争型で「相手が先にゴールしたら明確な敗北」とする。
2. ライフ／挑戦回数制（案2）を導入し、尽きたら敗北とする。
3. 負けを実装せず、代わりに「早くゴールするほど報酬が良い」スコア制にする。

**「負けが存在しない」を選ぶ場合**、`docs/04_test-plan.md` のシナリオ2
「プレイヤーが負けるまでの1試合」がそもそも書けなくなる。これはテスト計画側にも
影響する決定であり、`/spec` で先送りにできない。

## 6.5 検証と補足（メイン）

節2の期待値・均衡は、報告を鵜呑みにせず**自分で解き直した。** 結果、均衡比率は一致したが、
**前提を1つ動かすと答えが変わる**ことが分かった。以下は再導出の結果と、そこから出た補足。

### 検証1: 均衡 2:2:1 は正しい（再導出して一致）

相対的な進み幅を利得とする零和ゲームとして解き直した。利得行列（行＝自分、列＝相手、
順に グー・チョキ・パー）は

```
        グー   チョキ   パー
グー  [   0,    +3,    -6 ]
チョキ[  -3,     0,    +6 ]
パー  [  +6,    -6,     0 ]
```

無差別条件（相手が何を出しても自分の期待利得が0）を立てると
`3p_チョキ = 6p_パー`、`3p_グー = 6p_パー` から `p_グー = p_チョキ = 2p_パー`、
和が1で **0.4 : 0.4 : 0.2**。節2.3 と一致する。
「頻度 ∝ 自分が倒す相手の歩数」（6:6:3）も、この解と一致することを確認した。

### 検証2: 【重要】ゴール条件を変えると均衡が変わる — 節2と節5は独立していない

節2.3 の計算は「相手より速く進むことに価値がある」＝**相対競争型**を暗黙の前提にしている。
節5 が挙げるもう一方の**絶対距離型**（相手の位置は関係なく、自分が何歩進めたかだけを見る）
では利得が零和でなくなり、**均衡が別の値になる。** 解き直すと、

| ゴール条件 | 利得 | 均衡 グー:チョキ:パー |
| --- | --- | --- |
| **相対競争型**（相手より先にゴール） | 自分の歩数 − 相手の歩数 | **0.4 : 0.4 : 0.2**（2:2:1） |
| **絶対距離型**（自分が何歩進めたか） | 自分の歩数のみ | **0.25 : 0.5 : 0.25**（1:2:1） |

絶対距離型では、相手の前進を止める価値が消えるため、グーの「保険」としての役割が薄れ、
**チョキが単独で半分を占める**形になる（`EV(グー)=3p_チョキ`, `EV(チョキ)=6p_パー`,
`EV(パー)=6p_グー` を等置。検算: p=(.25,.5,.25) で3手とも期待歩数1.5で無差別）。

**つまり「ゴール条件をどちらにするか」（節5）は、UIの都合ではなく読み合いの形そのものを変える。**
`/spec` では節5のゴール条件を先に決めないと、節2の分析がどちらの数値で効くのかが定まらない。

### 検証3: 「相手がランダムならチョキとパーは互角」は絶対距離型でのみ成り立つ

節2.2 は自分の歩数だけを見ているため「チョキ=パー=2.0」になる。
相対競争型で解き直すと**互角ではない。**

```
相手が完全ランダムのときの相対期待利得
  グー   = (0 + 3 − 6)/3 = −1.0
  チョキ = (−3 + 0 + 6)/3 = +1.0   ← 単独で最良
  パー   = (6 − 6 + 0)/3 =  0.0
```

パーは勝てば6歩だが、負けるとチョキに6歩渡すため差し引き0になる。
**レースにするならチョキが単独最良**であり、初手の推奨が変わる。
「グーが損」という結論だけはどちらの前提でも変わらない。

### 検証4: あいこは1/3より多く出る（36〜38%）

均衡で打ち合うとあいこ率は `p_グー² + p_チョキ² + p_パー²` になる。

- 相対競争型 (2:2:1) → 0.16 + 0.16 + 0.04 = **36%**
- 絶対距離型 (1:2:1) → 0.0625 + 0.25 + 0.0625 = **37.5%**

手が均等（1/3ずつ）なら33%なので、**非対称であること自体があいこを増やす。**
節5 の「あいこの扱い」は、体感で3回に1回以上起きる頻出イベントとして設計する必要がある
（`docs/04_test-plan.md` のシナリオ3が想定する「あいこ連続」も、稀な例外ではなく日常）。

### 検証5: 【テンポの警告】1ターンあたり平均1.4〜1.5歩しか進まない

均衡で打ち合ったときの1ターンあたりの前進期待値を計算した。

```
相対競争型 (2:2:1):
  p_グー·p_チョキ·3 + p_チョキ·p_パー·6 + p_パー·p_グー·6
  = 0.16×3 + 0.08×6 + 0.08×6 = 0.48 + 0.48 + 0.48 = 1.44 歩/ターン
絶対距離型 (1:2:1): 同様に 1.5 歩/ターン
```

（均衡では3つの項がすべて 0.48 で等しくなる。無差別条件の裏返し。）

**歩数は6まであるのに、実際に進むのは1ターン1.4歩程度。** 勝てるのが約1/3しかないため。
これはテンポに直結する。**ゴール距離 ÷ 1.45 ≒ 必要ターン数**が目安になり、

- 案1の例にある**ゴール60歩は約42ターン**。1試合としては長すぎる
- 案2の例にある**関門20歩でも約14ターン**。関門1つでこの長さ

3日で作る規模なら、**ゴール距離は10〜20歩（7〜14ターン）が現実的な出発点**。
これは `/balance` ではなく `/spec` で当たりを付けておくべき数字（距離設定が
案の選択そのもの——1試合の重さ——に効くため）。

### 採用しなかった記述

- **節2.4 の `nabenavi.net` 由来の記述**（最適戦略が残り距離で動く／遠いときは1/3に近づく）は、
  **出典が Sources に載っておらず、確認できない。** さらに「両者がゴールから遠いときは
  1/3ずつの均衡に近づく」という部分は、**節2.3 の導出（遠い＝歩数が線形に価値を持つ状況で
  2:2:1）と正面から矛盾する。** 伝聞として扱い、設計の根拠にはしない。
  ただし「**ゴール直前は残り歩数が足りてしまうため手の価値差が消える**」という終盤効果自体は
  独立に成り立つ（あと3歩ならグーでもチョキでも勝ちは勝ち）。この形でなら使える。
- **節4 の「95%勝率」**（Nature Scientific Reports 2020）は数値を検証していない。
  ただし「履歴を読むAIは人間相手に強くなりすぎる」という論旨自体は、
  節4の「強すぎる境界」の警告として成立するので、数値を伏せて使えばよい。

## 7. 所感（選ぶときに効く軸）

案の優劣ではなく、選ぶ際に効きそうなトレードオフを挙げる。

- **「戦闘を持つかどうか」自体がスコープを最も左右する。** 案4のように別立ての戦闘フェーズを
  持たせると、実装量はほぼ2倍近くに膨らむ。持たせない場合は、グリコの読み合いそのもの
  （節2の非対称構造・節4のCPU設計）にリソースを全振りできる。
- **「探索の自由度」と「実装コスト・テストのしやすさ」はトレードオフになる。** 分岐マップ
  （案3）は探索としては最も豊かだが、`docs/04_test-plan.md` の「`tests/scenario/` は3本まで」
  という方針と衝突しやすい。分岐が増えるほど「決着時の状態」を一意に定義しづらくなる。
- **「CPUの読み合いの深さ」と「決定的な再現性」も綱引きになる。** 対プレイヤー履歴反応型
  （節4のc方式）は読み合いとして強いが、履歴という状態が増えるほど `rng` のシード固定だけでは
  足りず、`tests/scenario/` で検証すべき分岐が増える。
- **「レベルアップで何が変わるか」を一言で言えるかどうかが、3日で作れる育成要素の分かれ目。**
  案1・案5は歩数・疲労上限という単純な数値に言い切れる。案3は「装備・アイテムの豊富さ」に
  言い切れる代わり、テーブル設計そのものに時間がかかる。
- **グリコの本質（あいこが無限に続きうる／負けの概念が薄い）は、RPGの「勝敗がはっきりつく」
  文法と地味に相性が悪い。** ここをどう決着づけるかで、`docs/04_test-plan.md` の3本の
  シナリオ（勝つ／負ける／あいこ連続でも進行する）がそのまま使えるかどうかが変わる。
  特に「負けの条件」を作らない設計を選ぶ場合は、テスト計画自体の見直しが要る。
