## じゃんけんを戦闘に組み込む方式の候補

5案を挙げる。優劣はつけない。実装コストは `src/domain/` に必要な状態（BattleState）の
増え方で見積もっている。状態が増えるほど、シナリオテスト（`tests/scenario/`）で
検証すべき分岐も増える点に注意。

---

### 案1: 素のじゃんけん即時判定型

三すくみの勝敗をそのままダメージに変換する、最もシンプルな方式。

| 項目 | 内容 |
| --- | --- |
| 1ターンの流れ | プレイヤーはグー/チョキ/パーのいずれかを選ぶだけ。敵も同時に手を決め、勝敗を即座に判定してダメージを与える。**具体例**: HP20・被ダメ計算用攻撃力5の敵に対し、プレイヤーがグーを選択。敵はチョキを選択 → プレイヤーの勝ち → 敵HP 20→15。次ターン、プレイヤーがパー、敵もパーであいこ → ダメージなしのまま次ターンへ。 |
| RPGとしての伸びしろ | 攻撃力・防御力をキャラごとに変えて「勝ったときのダメージ量」に反映できる。スキルは「特定の手を出したときだけ発動」という形で乗せられる。ただし三すくみの構造自体が単純なため、敵の個性は「攻撃力の数値」と「手の出し方の癖」程度に留まりやすい。 |
| 実装コスト | 最も軽い。BattleState は `playerHp, enemyHp, playerAtk, enemyAtk, turnCount, handHistory` 程度。`resolveTurn(state, playerHand, rng) => BattleState`、`judgeHand(a, b) => 'win' \| 'lose' \| 'draw'`、`decideEnemyHand(state, rng) => Hand` の3関数で足りる。乱数は敵の手決定の1箇所のみ。3日規模に最も収まりやすい。 |
| 運ゲーになりにくさ | 敵が完全ランダムなら1/3の運そのもの。敵に「直前に負けた手を出しやすい」等の癖を持たせ、プレイヤーが手の履歴（`handHistory`）を見て読めるようにすれば運は薄まる。ただしダメージ量が固定だと「読みが当たったか外れたか」以外に判断材料がなく、駆け引きの深さは他案より浅い。 |
| 相性の悪い点 | 「なぜその手を選ぶか」の理由が読み合い以外にないため、スキルを乗せても本質的には運頼みの当てっこになりやすい。あいこ連続への対策をしないと単調になる。 |

- **あいこの扱い**: 双方ノーダメージのままターンを消費して進行。無限ループの懸念はターン数上限で保険をかける。あいこが続くほど双方に微ダメージを与える「疲労」ルールを足せば決着を早められる（任意）。
- **敵の手の決め方**: 「直前に負けた手を再び出しやすい」「同じ手を連続で出しにくい」など軽い重み付けを持たせ、プレイヤーが履歴から対応できるようにする。

### 案2: 手固有スキル型（三すくみ＋手ごとの固有効果）

グー/チョキ/パーそれぞれに固有の性能（威力・命中・追加効果）を持たせ、勝敗は威力倍率に反映する。

| 項目 | 内容 |
| --- | --- |
| 1ターンの流れ | プレイヤーは性能の異なる3つの手から選ぶ（例: グー=高威力・低命中、チョキ=連続2回攻撃・低威力、パー=威力低いが被ダメ軽減/回復）。じゃんけんの勝敗が威力倍率（勝ち1.5倍・あいこ等倍・負け0.3倍など）を決める。**具体例**: HP20の敵に対し、プレイヤーはチョキ（基礎威力3×2回）を選択、敵はグーを選択 → チョキはグーに負けるので倍率0.3倍 → 0.9ダメージ×2回で敵HP20→18程度。次ターン、敵がパー・プレイヤーがグーで勝ち、基礎威力5×1.5倍=7.5ダメージが入る。 |
| RPGとしての伸びしろ | 各手に固有効果を持たせることで、スキル・装備が「どの手を強化するか」という形で乗る（武器Aはグーの威力+50%、防具Bはパーの回復量増加、など）。敵ごとに「グーに弱い」「チョキを多用する」といった個性を出しやすく、5案の中では敵の個性が最も表現しやすい。 |
| 実装コスト | 中〜やや重い。BattleState は案1に加えて命中判定・状態異常・連続攻撃回数などを持つ必要がある。`HandProfile: { hand: Hand, power: number, hitRate: number, effect?: ... }` を `src/data/` に定義し、`resolveTurn(state, playerHand, enemyHand, rng) => BattleState` で命中判定にも乱数を使う（乱数箇所が2種類に増える）。3日には収まる見込みだが、連続ヒットなどの演出をUIに足すと時間を食う。 |
| 運ゲーになりにくさ | 「どの手を選ぶか」自体に戦術的な意味（重いが外れやすい/守りに回る、等）が生まれるため、単純三すくみより判断の幅は広い。ただし命中率という新しい乱数要素を足すと、じゃんけんの運＋命中の運の**二重運ゲー**になる危険がある。命中率を極端に低くしない等、数値設計の注意が必要。 |
| 相性の悪い点 | 手ごとの性能差が大きいと「実質グー一択」のような支配戦略が生まれ、三すくみ性が形骸化するリスクがある。バランス調整の負荷が他案より重い。 |

- **あいこの扱い**: あいこ時は倍率を等倍にし、通常ダメージを与える（グー同士ならグーの効果がそのまま出る）。あいこでも各手の個性が発揮されるため退屈になりにくい。
- **敵の手の決め方**: 敵の「得意な手」を重み付けし、得意な手のときは効果を強化する（炎の敵はグー＝火力特化を高確率で選ぶ、など）。プレイヤーは敵の属性を見て身構える読み合いができる。

### 案3: カード制限型（カイジ「限定じゃんけん」型）

戦闘開始時に決まった枚数の手札（例: グー×3・チョキ×2・パー×2）を持ち、1手ごとに消費する。資源管理の判断を足す。

| 項目 | 内容 |
| --- | --- |
| 1ターンの流れ | プレイヤーは残り手札の中から1枚を選んで消費する。在庫が尽きた手は選べない。**具体例**: 手札 グー3/チョキ2/パー2 で開始。1ターン目、敵がグーを出しがちな傾向を見てチョキを選択（残チョキ1）→勝利。2ターン目、チョキを温存したいが残弾が心配なため、あえてグーを出す（残グー2）という資源配分の判断が生まれる。 |
| RPGとしての伸びしろ | 装備・スキルで「手札構成を変える」（上位武器を装備するとグーが+1枚）、アイテムで「手札を1枚補充する」といった育成要素をカード構成の強化として乗せられる。敵側にも手札制を導入すれば「相手の残弾を読む」高度な読み合いになるが、実装コストはさらに増す。 |
| 実装コスト | BattleState に `playerHandCounts: { guu: number, choki: number, paa: number }` を追加（敵側も持たせるなら倍増）。`resolveTurn(state, playerHand, rng) => BattleState` の内部で「在庫0の手は選べない」バリデーションが必要になり、`selectableHands(state) => Hand[]` のようなUI補助関数も要る。**敵にも手札制を課すかどうかで実装コストが大きく変わる**。敵を無限手（案1相当）にすれば軽いが、カイジ型の醍醐味（互いの残弾読み合い）は薄れる。敵にも手札制を課すと「残り枚数から出す手を選ぶ」AIロジックとその分岐テストが増え、3日規模ではやや重い。 |
| 運ゲーになりにくさ | 「残り枚数」という有限リソースの管理が発生するため、単なる勝率予想ではなく資源配分の判断に変わる。終盤ほど相手の手が絞り込め（残弾からロジックで推測できる）、じゃんけん単体より明確に運が薄まる。原作のカイジもこの資源制限が読み合いの核。 |
| 相性の悪い点 | 1戦闘の手数が少ないと読み合いが始まる前に決着してしまう。逆に手数を増やすと補充ルールが必要になり設計が複雑化する。雑魚戦を何度もこなすテンポとは相性が悪く、ボス戦向きの重い仕組みになりやすい。 |

- **あいこの扱い**: あいこでも手札を消費する方向が安全（消費しないと「あいこを繰り返して手札を減らさず様子見」という戦略が成立し、決着が長引く・引き分け狙いのループが起きうる）。ターン数上限も併用して保険をかける。
- **敵の手の決め方**: 敵の手札構成をあらかじめ偏らせる（常にグーが多い敵、等）ことで、プレイヤーが「敵の残弾から詰めていく」読み合いを成立させる。敵に手札制を課さない場合は案1同様、重み付けランダムで代用する。

### 案4: 行動権争奪型（じゃんけんは先制/追加行動のみ決定）

じゃんけんの結果はダメージ量に直接影響させず、「行動順」だけを決める。ダメージ本体は別途スキル選択で決まる。

| 項目 | 内容 |
| --- | --- |
| 1ターンの流れ | プレイヤーはまずスキル/通常攻撃を選び、そのあとじゃんけんで行動順を決める。勝った側が先に攻撃し、負けた側は後手に回る。**具体例**: HP20の敵に対し、プレイヤーは「強攻撃（威力8・コスト高）」を選択。じゃんけんでグーを出し、敵はチョキを出す→プレイヤー勝利で先制権獲得。強攻撃が先に命中し、敵HP20→12。じゃんけんに負けていれば、敵の攻撃が先に処理されてからプレイヤーの強攻撃が発動する、という順序の違いだけが生まれる。 |
| RPGとしての伸びしろ | スキル選択（通常攻撃・強攻撃・防御・回復など）とじゃんけんの結果（行動順）を分離しているため、既存のターン制RPGの資産（スキルツリー、MP消費、状態異常、装備効果）をほぼそのまま乗せられる。Persona/女神転生系のプレスターンのような拡張（勝てば追加行動、大敗すれば行動キャンセル）も可能で、5案の中で最もオーソドックスなRPGに近づけられる。 |
| 実装コスト | **最も重い**。BattleState に `playerMp, statuses, selectedSkill, turnCount, history` などが必要。`resolveTurn(state, playerHand, playerSkill, rng) => BattleState` は行動順制御を含み、`decideEnemyHand` と `decideEnemySkill` を両方持つ必要がある。加えてスキルシステム自体（威力・コスト・対象・MP管理）を並行して作り込む必要があるため、**じゃんけん部分は軽くても、RPGの土台づくりが別に発生する**。3日規模だと「じゃんけん」と「スキル制RPG」を両方一から作ることになり、スコープが膨らみやすい。 |
| 運ゲーになりにくさ | ダメージの本体はスキル選択（プレイヤーの判断）に委ねられ、じゃんけんは「先手・後手」という副次効果に限定されるため、じゃんけんの運が結果に与える影響は他案より薄い。ただし裏を返すと、じゃんけんの存在感が薄れ「なぜじゃんけんをやっているのか」がぼやける可能性がある。 |
| 相性の悪い点 | じゃんけんがおまけ要素になりやすく、ゲームの主役が「スキル選択とMP管理」に寄ってしまうと、じゃんけんRPGとしてのアイデンティティが薄れる。実装量（スキルシステム）が他案より確実に重く、3日で作り切るには機能を絞る判断が必須。 |

- **あいこの扱い**: あいこの場合は「同時発動」として両者が同時に攻撃処理する（先制ボーナスなし）。無限ループの心配はなく、あいこでも普通にターンが進む。
- **敵の手の決め方**: 敵のスキル選択とじゃんけんの手を連動させる（強い技を溜めているときは先手を譲りたくないのでグーを出しやすい、等）ことで、「今回は強い技を溜めてきたから先手を取られたくない」という読みをプレイヤーに与えられる。

### 案5: 予兆読み型（ヒント/後出し型）

敵が手を出す前に、一定確率で「次に出す手のヒント」を提示する。読みの精度を確率で操作する方式。

| 項目 | 内容 |
| --- | --- |
| 1ターンの流れ | ターン開始時、画面に「次に出す手のヒント」（例: アイコンで「炎の構え＝グー系」を示唆）が一定確率で表示される。プレイヤーはヒントを踏まえて自分の手を選ぶ。ヒントは外れる（フェイク）こともある。**具体例**: HP20の敵。ヒントが「グー系の構え」を示す。プレイヤーはこれを信じてパーを選択し、実際に敵がグーを出せば勝利してダメージ。次ターンはヒントが出ない（不確実ターン）ため、プレイヤーは手の履歴から確率的に判断するしかない。 |
| RPGとしての伸びしろ | 「ヒントの精度」を敵の個性として設定できる（このボスはヒントが常に正しい/この雑魚はヒントがよく外れる、など）。プレイヤー側のスキルや装備で「ヒントの的中率を上げる」「ヒントをもう1つ増やす」といった支援効果を乗せられ、育成要素とじゃんけんの読みを直結させやすい。 |
| 実装コスト | BattleState に `revealedHint: Hand \| null, hintAccuracy: number` などを追加。`decideEnemyHand(state, rng) => Hand` に加え `generateHint(enemyHand, hintAccuracy, rng) => Hand \| null` という**ヒントの当たり外れ用の乱数**が別途必要になり、乱数箇所が2系統に分かれる。敵の手そのものの乱数とヒントの乱数を独立させるため、シード管理・再現性テストがやや複雑になる（案1より `tests/unit/` で検証すべき分岐が増える）。UI側もヒント表示の演出が要り、UI実装コストも増える。 |
| 運ゲーになりにくさ | ヒントという部分的な情報を与えるため、単純な1/3の運から「情報を元にした期待値計算」に変わる。的中率が高いほど運は薄まるが、低いと結局運ゲーに近づく。**的中率の数値設計がそのままゲーム全体の運の強さを決める**ため、バランス調整の比重がここに集中する。 |
| 相性の悪い点 | ヒントの信頼性を疑似乱数で作り込むため、プレイヤーから見て「ヒントの意味」が体感しづらいと単なる運要素に見えてしまう危険がある。ヒントUIを分かりやすく提示する必要があり、ビジュアル面の作り込みに時間を取られやすい。3日規模だと凝ったヒントUIを作る余裕がなく、「地味で伝わらないヒント」になるリスクがある。 |

- **あいこの扱い**: あいこの場合はヒントを次ターンに持ち越さず毎ターンリセットする。無限ループ防止のためターン数上限は他案同様に必要。
- **敵の手の決め方**: 敵の「素の手の決定」は案1と同様の重み付けランダムをベースにし、そこにヒント生成ロジックを被せる二層構造にする。

## 参考にした既存ゲーム

- **賭博黙示録カイジ「限定じゃんけん」** — プレイヤーはグー/チョキ/パーのカードを固定枚数（例: 各数枚）しか持たず、使い切ると負ける。手札という有限資源が読み合いの核になっており、**案3（カード制限型）**の直接の参考元。カード・スターの取引や裏切りの駆け引きなど、対人心理戦の要素が強い点は今回のRPG（対NPC戦）にはそのまま持ち込めないが、「残り枚数が減るほど選択肢が絞られ、運が薄まっていく」という構造自体は流用できる。
- **ポケモンのタイプ相性（三すくみの拡張）** — 属性同士が三すくみ以上の多角関係を持ち、技・装備の選択に組み込まれている。じゃんけんそのものではないが、「手＝属性」「勝敗＝ダメージ倍率」という構造は**案2（手固有スキル型）・案5（属性拡張の応用）**の参考になる。相性が育成（技構成・パーティ編成）と直結している点が、じゃんけんをRPGの育成要素と噛み合わせるうえで参考になる。
- **女神転生/ペルソナ系のプレスターン制** — 弱点を突くと追加行動が得られ、外すと行動権を失う。じゃんけんの勝敗を「ダメージ」ではなく「行動権」に変換する発想は**案4（行動権争奪型）**そのものの先例。スキル選択とターン管理が主役で、属性相性（＝じゃんけん要素）は行動権を左右する副次要素という位置づけが、案4の設計思想と一致する。
- **rock paper scissors 系のデッキビルド系インディーゲーム（例: itch.io の "Rock Paper Scissors Go!"）** — 勝つとカードが増え、じゃんけんの手そのものが「グー/チョキ/パー」から拡張されていくローグライク。じゃんけんの手を育成要素として扱う発想は**案2・案3**の拡張案として参考になる。
- **ボードゲーム設計フォーラム（BGDF）の RPS カードコンバット議論** — 「手の種類を3種以上に増やすと初見のプレイヤーが混乱しやすい」「三すくみの各要素を別のリソース（俊敏/知力/腕力など）に紐付けると理解しやすい」という指摘があり、**手を増やしすぎない**（3種を保つ）ことの妥当性を裏付ける参考になった。

## 検証と補足（メイン）

上の5案は `battle-research` が洗い出したもの。実装コストの見積もりを検証したところ、
3点の見直しと、案の並べ方そのものへの補足が要ると判断した。**ここでも案は絞らない。**

### 見直し1: 案2 の実装コストは「中〜やや重い」ではなく、案1 とほぼ同じ

案2 が重く見積もられているのは、調査が**命中率・状態異常・連続攻撃を案2に含めてしまった**ため。
これらは案2 に必須ではない。じゃんけんの勝敗を倍率に変えるだけなら、増える状態は 0 で、
増えるのは `src/data/hands.ts` のテーブル1枚に過ぎない。

```ts
// domain の関数シグネチャは案1 と同一。乱数箇所も敵の手決定の1つだけ
resolveTurn(state, playerHand, rng) => BattleState
```

**この形の案2 は、CLAUDE.md のレイヤ規約と最も噛み合う。** 手の性能が全部 `src/data/` に
乗るので、バランス調整がロジックを一切触らずに回せる。命中率を足した瞬間に乱数が
2系統になり、二重運ゲーの危険と再現テストの複雑さを同時に抱え込む。
**案2 は「命中率あり」と「命中率なし」で別案として扱うべき。**

### 見直し2: 案3 に穴がある — 手札が尽きたときが未定義

調査は「あいこでも手札を消費する」と書いているが、**全部の手札を使い切ったときどうなるかを
書いていない。** 手札を消費し続ける以上これは必ず起きる。決めていないと、
選べる手が 0 の状態でターンが回り、`tests/scenario/` の「あいこが連続しても進行する」が
ハングとして落ちる。取りうる選択肢は次のどれかで、**どれを選ぶかで戦闘の性格が変わる。**

| 手札切れの扱い | 戦闘の性格 |
| --- | --- |
| 手札切れで敗北 | 決着が確実につく。1戦が短く緊張する。カイジに最も近い |
| 手札切れで全補充 | 実質「手数に区切りのある案1」。長期戦になる |
| 毎ターン1枚ずつ補充 | 資源管理が薄まる代わりにテンポが安定する |

**案3 を採るなら、この表のどれかを `/spec` で決めきる必要がある。** 見積もりコストは
調査の記述に、この決定と実装の分を上乗せして読むこと。

### 見直し3: 案4 は「重い」だけでなく、じゃんけんが結果に効かない構造をしている

1対1の戦闘で、双方が毎ターン必ず1回行動するなら、**先手と後手の違いが結果を変えるのは
「その一撃で相手が倒れるとき」だけ。** それ以外のターンでは、順番が入れ替わっても
最終的な被ダメージ総量は変わらない。つまり案4 は、実装が5案で最も重いにもかかわらず、
**じゃんけんの勝敗がほとんどのターンで無意味になる。**

調査もこれを「じゃんけんの存在感が薄れる」と書いているが、体感の問題ではなく構造の問題。
効かせるには「勝てば追加行動」「大敗すれば行動キャンセル」（プレスターン型）まで
踏み込む必要があり、そこまでやると実装量はさらに増える。
**案4 は「重いから避ける」ではなく、「重いうえに、軽い版では成立しない」として評価すべき。**

### 補足: 案5 は他案と並ぶ選択肢ではなく、上に重ねられる層

案1〜4 は「じゃんけんの勝敗を何に変換するか」という同じ軸の上にある。
案5（予兆読み）はそこではなく、**「プレイヤーにどれだけ情報を与えるか」という別の軸**にある。
案5 は案1 にも案2 にも案3 にも乗る。5案を横一列に並べて1つ選ぶ形にすると、この重なりを見落とす。

整理すると、決めることは1つではなく3つある。

| 軸 | 選択肢 |
| --- | --- |
| **A. 勝敗を何に変えるか** | ダメージそのもの（案1）／ダメージ倍率（案2）／行動順（案4） |
| **B. 手の選択に制約をかけるか** | 制約なし（案1・2・4）／手札制（案3） |
| **C. どこまで情報を見せるか** | 履歴だけ／ヒントあり（案5） |

`/spec` ではこの3軸それぞれを決める。**A を決めれば B・C は「乗せない」も選べる**ので、
最小構成は「A=倍率、B=なし、C=履歴だけ」になる。

### 全案に共通する、調査に出ていない論点

- **UI の実装コストは、どの案でもテストに守られない。** `docs/04_test-plan.md` の通り
  `src/ui/` にテストは書かない。案が重くなるとUIも重くなるが、その分は自動検証されず、
  手動のブラウザ確認3回に全部乗る。**domain の軽さだけで案を選ぶと、ここを見誤る。**
- **同時出しであることを演出で壊さない。** 案1・2・3 は敵とプレイヤーが同時に手を決める前提。
  UI で敵の手を先に見せると後出しが成立して読み合いが消える。domain は同時のままでよいが、
  **表示順は設計で縛る必要がある**（`docs/03` に書く事項）。
- **成長要素をどこに乗せるかは、A の選択でほぼ決まる。** 案1 は数値（攻撃力）にしか乗らない。
  案2 は手ごとの性能に乗る。案3 は手札構成に乗る。**「レベルアップで何が変わるのか」を
  一言で言えるかどうか**が、3日で作れる育成要素になるかの分かれ目になる。

## 所感

案の優劣ではなく、選ぶ際に効きそうな軸を挙げる。

- **選択の重さ と 実装コストはトレードオフになりやすい。** 案1（即時判定）は軽いが「手を選ぶ理由」が読み合いだけに依存し薄い。案3（カード制限）・案5（予兆読み）は選択の意味が濃くなる分、状態（手札残数・ヒントの当たり外れ）が増え、`domain/` のテストすべき分岐も増える。
- **「じゃんけんの存在感」と「RPGとしての厚み」も綱引きになる。** 案4（行動権争奪型）はスキルシステムというRPGの土台を丸ごと作る必要があり、RPGとしての厚みは出しやすい反面、じゃんけんが「先手を決めるだけの前座」になりやすく、ゲームのアイデンティティが薄れるリスクがある。逆に案1・案2はじゃんけんそのものが主役であり続けられるが、RPGらしい育成の乗せ方は工夫が要る。
- **あいこの扱いの軽重が案によって大きく違う。** 案1・案2は「ダメージなしで次ターンへ」で済むが、案3はあいこ時に手札を消費するかどうかを決めないと、あいこを繰り返すだけの引き分け狙い戦略が成立してしまう。あいこの扱いは軽視できず、`docs/04_test-plan.md` の「あいこが連続しても進行する」テストの複雑さに直結する。
- **乱数箇所の数がテストの複雑さを左右する。** 案1・案3は乱数が「敵の手の決定」1箇所で済むが、案2は命中判定、案5はヒントの当たり外れが加わり、乱数箇所が2系統以上になる。`src/lib/rng.ts` 経由であればどの案でも再現性は担保できるが、シードから「何が起きるか」を追うテストコード自体は乱数箇所が増えるほど書く量が増える。
- **3日で作れるかどうかの分水嶺は、BattleState に持たせる状態の種類の数にほぼ比例する。** 案1（3〜4フィールド）が最も軽く、案4（スキルシステム一式）が最も重い。案3・案5は「プレイヤー側だけ簡易に実装する」「ヒントの確率を単純な固定値にする」など機能を絞れば3日規模に収まる余地はあるが、豪華にしようとするとすぐに膨らむ。
