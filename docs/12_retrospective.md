## 2. ハーネスの構成物

5種類ある。**それぞれ役割が違い、重なっていない。**

| 構成物 | 実体 | 何を担うか |
| --- | --- | --- |
| 規約 | `CLAUDE.md` | 常時効くルールだけ。レイヤ規約、絶対に守ること |
| 手順 | `docs/10_workflow.md`, `docs/11_delegation.md` | 工程に入るとき・委譲する前に読むもの |
| コマンド | `.claude/commands/*.md` | 1工程の進め方。**何を委譲し、何を自分で持つかの線引き** |
| エージェント | `.claude/agents/*.md` | 委譲先の人格と禁止事項 |
| 自動検査 | `.claude/hooks/check.sh`, `scripts/check-layers.sh` | 判断が要らない検査。**トークン0で回る** |

### CLAUDE.md を痩せさせたこと

初期の CLAUDE.md には手順まで書いていたが、途中で `10_workflow.md` と `11_delegation.md` に
切り出した（`6644b8e`）。**常時読まれるファイルに、たまにしか要らない手順を置くと毎回コストを払う。**
CLAUDE.md には「読む先の表」だけを残し、詳細は必要なときだけ読ませる形にした。

### hook（`.claude/hooks/check.sh`）

`.ts` を Edit / Write した**直後**に、型チェック → 関連テスト → レイヤ規約を回す。
失敗したら終了コード 2 で stderr を返し、その場で直させる。

**壊れたことを人間が見つけて指摘する手間をなくすのが目的。** 「後でまとめて `npm run check`」だと、
壊した箇所と気づく時点が離れて切り分けが高くつく。

> **注意（実際に踏んだ）**: hook は Claude の Edit / Write ツールに紐づいているので、
> `codex exec` の書き込みには**発火しない**。Codex から戻ったら手動で
> `git diff --stat && npm run check && git diff tests/` を回す必要がある。

### `scripts/check-layers.sh`

grep で判定できるレイヤ規約違反（`domain/` からの `src/data/` import、`Math.random()` の直呼び等）を
シェルスクリプトで検査する。**モデルに読ませる前に、スクリプトで書けないかを先に考える。**
書けるならトークンは0になり、しかも決定的に落ちる。

### `AGENTS.md`（Codex 向け）

Codex は `CLAUDE.md` を読まないので、規約を Codex 向けにもう1枚用意した。
最も重要なのはこの一節。

> **テストが通る間違った実装は、通らない実装より悪い。**
> 製品に残り、しかもテストがもう守ってくれない。

`if (hp < 0) hp = 1;` のような「緑にするだけの修正」を名指しで禁止し、
**通し方が分からないときは無理に通さず手を止めて報告する**ことを完了条件に入れた。

## 3. コマンドの中身

7つ。工程の順に並ぶ。

```
/research → /spec → /design → /test → /impl → /conform → /balance
```

**すべてのコマンドが「委譲する部分」と「自分で持つ部分」を明記している。**
これがこのハーネスの背骨で、軸は1つ — **残っている仕事が「読むこと」か「決めること」か。**

| コマンド | 委譲する（安いモデル） | 自分で持つ（Opus） |
| --- | --- | --- |
| `/research` | 案の洗い出し — `battle-research` (sonnet) | 実装コストの検証、比較表での提示 |
| `/spec` | 抜け漏れの検査 — `spec-review` (haiku) | **案の選択、ADR、「やらないこと」** |
| `/design` | **なし** | **全部** |
| `/test` | テストの記述 — `test-designer` (sonnet) | 期待値の根拠が設計にあるかの確認 |
| `/impl` | 実装 — Codex (gpt-5.6-luna) | 差分の確認、**エラー時の切り分け** |
| `/conform` | 適合検査 — `design-conformance` (haiku) | 指摘の採否 |
| `/balance` | 数値の書き換え — Codex (luna) | 問題の言語化、**プレイしての確認** |

### `/research` — 案を洗い出す。絞らない

sonnet に4案以上出させ、`docs/00_research.md` にまとめさせる。
**絞るのは `/spec` の仕事**と明記して、発散と収束を分けている。

> 起動後に必ずやること: **実装コストの見積もりを自分で検証する。**
> sonnet は「3日で作れる」と楽観的に書きがち。実際 `docs/00_research.md` 節6.5 では
> 期待値の計算を自分で解き直して誤りを見つけている。

### `/spec` — 1案に確定し、ADR に却下理由まで書く

決定は Opus が持つ。**「やらないこと（OUT OF SCOPE）」を要件定義の本体**と位置づけた。
haiku の `spec-review` は**列挙するだけで決めない**設定にしてある。

ここで書いた ADR 0001 は最後まで覆していない。

### `/design` — 唯一、委譲しない工程

理由を2つ書いてある。

1. **手戻りが最も高い。** 設計を変えると domain も data もテストも全部書き直しになる。
2. **下流がこの精度に依存する。** `/test` はここからテストを書き、`/impl` は Codex が
   これだけを見て実装する。曖昧なまま流すと、曖昧さが増幅されて返ってくる。

合格ラインは **「Codex が読んで実装できる粒度」**。自己確認の質問を3つ置いた
（具体例を1つ書けるか / 境界で何が起きるか / 乱数を `Rng` で受け取る形か）。

### `/test` — 実装より先に、別のモデルで書く

**実装と同じモデルにテストを書かせると、「仕様通りか」ではなく「実装した通りか」を
検証してしまい、バグを追認する。**

この工程だけは `npm run check` が赤のままコミットする（唯一の例外）。理由は2つ。

1. `/impl` の前にコミットしておかないと `git diff` が「Codex が書いたもの」にならない
2. テストが先にコミットされていることが、**実装がテストに合わせた証拠**になる

赤の中身が「実装がまだ無い」ことだけを指しているかは、次で判定する。

```bash
npx tsc --noEmit 2>&1 | grep '^src/' || echo "エラーは tests/ だけ = 正しい状態"
```

`tests/scenario/` については2点を必ず見る。**ターン数の上限があるか**（無いとあいこ無限ループで
テストがハングする）、**途中経過の数値を検証していないか**（`src/data/` を触るたび壊れて
バランス調整ができなくなる）。

### `/impl` — 1モジュールずつ。渡す前に必ずコミット

内側から外側へ（domain → data → application → ui）。まとめて渡さない。

```bash
git add -A && git commit -m "wip: <直前までの内容>"
codex exec --model gpt-5.6-luna --full-auto "<設計のどの部分を実装するか>" < /dev/null
git diff --stat && npm run check && git diff tests/
```

- **`< /dev/null` は必須。** 付けないと Codex が stdin を待って止まる
- **規約をプロンプトに書き写さない。** `AGENTS.md` が持っている
- 渡すときは **「触れてよいファイル」と「あるべき挙動」を両方書く。**
  範囲を切らないと別の層を壊し、あるべき挙動を書かないと緑にするだけの修正が返る

失敗したときの担当は2段階で決める。**「どちらが安いか」ではなく「読む仕事か決める仕事か」。**

| 段階 | 判定 | 担当 |
| --- | --- | --- |
| 第1 | 型エラー・レイヤ規約違反・スタックトレース（原因箇所が出る） | luna に直接差し戻す |
| 第1 | アサーション失敗・ハング（期待値と実測値だけ） | 自分で読む → 第2段階 |
| 第2 | 原因も直し方も分かった | **自分で直す。**渡すと往復のほうが高い |
| 第2 | 見当はつくが、確定にはコードを読む必要がある | **luna に渡す。**ここが本来の使いどころ |
| 第2 | 見当もつかない | **`docs/03` を疑う。**設計の穴かもしれない |

### `/conform` — 適合検査。指摘は鵜呑みにしない

haiku の `design-conformance` は**コードを書き換えない**設定。
エージェントは実装の意図を知らないので、意図的な判断を違反と誤認する。
**まず自分でコードを読んで裏を取ってから採否を決める。**
設計側が古いことが原因なら、コードではなく `docs/03` を直す。

### `/balance` — 触ってよいのは `src/data/` の中だけ

数値の書き換えは機械的なので Codex に出す。ただし
**「何が問題か（強すぎる/弱すぎる/単調）」の言語化と、実際にプレイしての確認は自分で持つ。**
数値が通ったことと面白くなったことは別。

### `/assets` — Claude では画像を生成できない

`asset-brief` (sonnet) に発注仕様（ファイル名・サイズ・プロンプト）を作らせ、
ユーザーが imagegen に投げて `public/assets/` に置く。
**素材待ちで実装を止めない。** プレースホルダで先に組み、後から差し替える。

## 4. 効いたこと

### テスト先行は効いた。ただし理由は「バグを防いだ」ではない

**実装コミット10本のうち、`tests/` に触ったのは1本だけ**（3行）。しかもその中身は
正しい訂正だった（scissors で勝たせたいのに敵の手を rock に固定していた。scissors が
勝てるのは paper）。`AGENTS.md` が警戒していた「緑にするだけの修正」は**一度も起きていない。**

効いた本体は次の3つ。

1. **テストが Codex への仕様書になった。** 実装が15分で終わったのはこれ。
   テスト 2,901行 / src 2,300行 という比率が、そのまま「先に固めた仕様の量」
2. **設計改訂の詰めを強制した。** ADR 0002 / 0003 / 0004 はどれもテストを先に全面改訂してから
   実装に渡している。`5f8782f` は「失敗は24件すべて tests/ に閉じている。既存の133件は
   1本も落ちていない」と書けている。**何が変わり何が変わらないかが赤/緑で見えた**
3. **別モデルに実装を任せるための前提条件だった。** Codex に渡す構成を採った時点で、
   テスト先行はほぼ必須だった

### 「まず測る」が判断を作った

ADR 4本はすべて計測が起点。

| きっかけ | 測ってから決めたこと |
| --- | --- |
| ADR 0001 の狙いが出ているか数万戦回した | ADR 0002「熱」 |
| 「熱がたまりまくって実質二択」という指摘 | ADR 0003「直近4手の窓」（式から必然だと確認） |
| 「敵の個性が薄い」という指摘 | ADR 0004「敵ごとの値表」（総変動距離で隔たりを数値化） |

**不満を言葉のまま受け取らず、必ず数字にしてから設計に落とした。**
`scripts/measure.ts` はテストと同じくらい効いた投資だった。

### 覆した決定も、やらないと決めたことも残した

ADR 0003 は ADR 0002 を一部覆しているが、消さずに「なぜ覆したか」を残している。
最後のコミット `1bb2133` は**「手の分布がチョキに寄っている件を放置する」という判断とその理由**。
決めたことと同じくらい、**決めなかったことの理由**が後から効く。

## 5. 効かなかったこと

正直に言うと、**プロジェクト後半（面白くする側）にテスト先行はほぼ効いていない。**

| 見つかり方 | 事例 |
| --- | --- |
| 計測 | ADR 0002 / 0003 / 0004 |
| 遊ぶ・見る | `385c9a1` 強化画面でグーが増えないように見える、`911e9fb` `93510a1` スマホの表示崩れ |
| テスト | 型・不変条件・式の一貫性 |

- **テストが「つまらない」と言ってくれたことは一度もない。**
  UI をテストしないのは `docs/04_test-plan.md` の意図的な判断なので想定内だが、
  結果として**面白さの担保は全部プレイ側にあった**
- **ハーネスの外側は守られなかった。** `1b7dcfa` は `scripts/measure.ts` 自体のバグで、
  `applyHeat(BASE_HANDS, ...)` と書いて `desperateBonus` を落とし、
  **本気の敵を弱く見積もったままバランスを判断していた**。テストは `scripts/` を見ていない
- **表示と domain が同じ式を別々に持っていた**（`69eb43a`）。5戦4,523ターン中426件ずれていた。
  テストは「設計が名前を付けたもの」しか守れない。`dealtDamage` という関数が
  設計に無かったので、テストも書きようがなかった

## 6. 次に持っていく原則

1. **コードより先にハーネスを作る。** 0日目の10コミットが、以降のすべての速度を決めた
2. **委譲の軸は「読む仕事か、決める仕事か」。** 安いか高いかではない
3. **判断が要らない検査は、モデルより先にスクリプトを疑う。** トークン0で決定的に落ちる
4. **設計だけは委譲しない。** 下流が全部この精度に依存する
5. **テストは実装と別のモデルに、先に書かせる。** 同じモデルだとバグを追認する
6. **不満は必ず数字にしてから設計に落とす。** 計測スクリプトはテスト級の投資価値がある
7. **テストが守るのは「設計が名前を付けたもの」だけ。** 面白さと表示は自分で見るしかない
8. **覆した決定と、やらないと決めたことを残す。** ADR は決定の置き場であり、履歴の置き場
