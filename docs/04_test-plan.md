# テスト計画

> ステータス: **ADR 0003 のぶんは実装待ち** — 130件のうち 27件が落ちている（`/test` 直後の正しい状態）。
> 落ちているのは**すべて ADR 0003 で作り替えた項目**で、`src/` 側は改訂前の設計のまま一貫している。
> 詳しくは末尾の「連打の窓への作り替え」。それ以前のぶんは緑。

## 3層の方針

| 層 | 置き場所 | 検証するもの | 自動化 |
| --- | --- | --- | --- |
| ユニット | `tests/unit/` | `domain/` の純粋関数、`lib/`、**`application/` の配線のうちシナリオでは見えないもの** | vitest |
| **シナリオ** | `tests/scenario/` | `domain` + `application` を通した戦闘1試合 | vitest |
| ブラウザ確認 | 手動 | UI を含めた画面遷移・表示・操作 | なし |

## 結合テストの範囲

**3日で作る規模なので、しっかりした結合テストは行わない。** そのぶん、
自動化できる範囲を `tests/scenario/` に寄せる。UI を含めない結合であれば
vitest で決定的に回せるため、コストがほぼかからない。

### `tests/scenario/` は3本まで

1. プレイヤーが勝つまでの1試合 — 決着時の状態
2. プレイヤーが負けるまでの1試合 — HP が負にならない、敗北状態になる
3. あいこが連続しても進行する — **無限ループにならない**（ターン上限で検出）

### バランス調整に耐えること

シナリオテストは**決着時の状態だけ**を検証する。途中の数値を検証すると、
`src/data/` の数値を変えるたびにテストが壊れ、バランス調整ができなくなる。

- 書く: 「決着したとき、勝者の HP が 1 以上」
- 書かない: 「3ターン目に HP が 12」

### ブラウザ確認は手動、回数を絞る

E2E フレームワークは導入しない（3日の規模に対して重い）。
次の3回だけ、開発サーバを起動して手で確認する。

1. 各画面が組み上がった時点
2. 全画面が繋がった時点
3. バランス調整の最終確認

## UI はユニットテストしない

`src/ui/` にテストは書かない。3日の規模ではコストが見合わないため、
ブラウザでの目視確認に任せる。そのぶん `domain` を厚く検証する。

### テストの前提として置いたこと（実装側が守るもの）

- **敵の手を固定する方法**: 重みを1つの手に集中させ（`weight = 1`、他 0）、
  `rng.next()` が `0.5` を返すようにする。`UNIFORM_MIX = 0.3` なので集中させた手の
  確率は 0.8 になり、必ずその手が選ばれる。**この性質は `docs/03` 節3 の式から導ける**
- **`resolveTurn` が決着済み state を返すときの参照同一性は縛っていない**（`toEqual` で検証）。
  同じ参照を返す実装と、同じ値の新しいオブジェクトを返す実装のどちらでもよい
- **シナリオ1・2 は勝ち／負けのシードを決め打たない。** 300シードを順に試し、
  最初に条件へ合致したものを検証する。見つからなかった場合は
  **「バランスの偏り」だと分かる失敗メッセージ**を出す（実装のバグと切り分けるため）

**`battle.test.ts` が本体。** 特にこの3つは落とさない。

- **相手が生き残るターンでは `playerHp + enemyHp` が必ず1以上減る**（終了保証）。
  **「毎ターン必ず減る」と書かないこと。** 相手を倒したターンだけは回復ぶんで総和が
  増えうる（節4の不変条件4）。ここを取り違えると、**正しい実装なのにテストが落ちる**
- **耐性0.5のパーで回復がダメージを上回らない**（例3。ここが壊れると戦闘が終わらない）
- **同時に0以下ならプレイヤーの敗北**（例5。引き分けを作らない）

また、**決着済みの `state` に `resolveTurn` を呼んでも `turn` は増えず、同じ state が返る**
（節4の手順0）。不変条件3・7は**未決着の state に対してのみ**成り立つ。

#### `tests/scenario/`

方針どおり**3本まで**。`application/game.ts` を通す。
固定シードで回し、**決着時の状態だけ**を見る。途中の数値は見ない。

1. プレイヤーが勝つまでの1周 — 5体倒して `phase === 'result'` かつ `cleared === true`
2. プレイヤーが負ける1試合 — `cleared === false`、`playerHp === 0`、HPが負になっていない
3. **あいこが連続しても進行する** — ターン上限（例: 200）を置いて回し、
   **上限に達する前に必ず決着すること**。にらみが `STARE_MAX` を超えないこと

### `application/game.ts` の配線のテスト（`tests/unit/game.test.ts`）

**シナリオテストは決着時の状態しか見ないので、熱の配線は素通りしてしまう。**
「戦闘ごとにリセットし忘れた」「敵側の熱を進め忘れた」は、それでも1周クリアできてしまうため
シナリオ3本のどれも落ちない。熱の実装の大半は `application` 側（`docs/03` 節5）にあるので、
**ここだけを対象にしたユニットテストを1本足した。**

| 検証するもの | 根拠（`docs/03` 節5） |

| `startGame` 直後は両方の熱が `NO_HEAT` | 各関数の表・不変条件 |

### シナリオテストは増やさない

**3本のまま。** ただしシナリオ3（あいこが連続しても進行する）は、
熱で全手が弱ると**1ターンあたりの減りが小さくなる**ため、
**ターン上限に達しないことの意味が重くなる**。既存のテストがそのまま効く。

### `domain/battle.ts` のテストは1本も変えない

熱は `application` が組み立てた `HandTable` として渡るだけで、
`resolveTurn` の契約は変わらない。**`tests/unit/battle.test.ts` に手を入れる必要が出たら、

**方針どおりテストでは検証しない**（`/balance` で動かせる状態を保つ）。

### 中心は「具体例の表」（`tests/unit/handTable.test.ts`）

`docs/03` 節2.5 の表を、**出し方1列につき `it` 1本**にした。
ADR 0003 の狙い（**均等回しと2連続は罰なし、3連続から罰**）がそのままテストの名前になっている。
どれが落ちたかが名前で分かるので、`/impl` の切り分けが速い。

| 出し方 | 期待する弱化の列 |
| --- | --- |
| 均等に回す グチパグチパグ | `0 0 0 0 0 0 0` |
| 2連続を挟む ググチパググチ | `0 0 0 0 0 0 0` |
| 3連続 グググチパグ | `0 0 1 0 0 0` |
| 同じ手だけ（6手） | `0 0 1 2 2 2` |
| 2手交互 グチグチグチ | `0 0 0 0 0 0` |

**`maxPenalty` は別のローカル `rule` で確かめている。** `window:4 / allowed:2` では
弱化が最大2までしか届かず `maxPenalty:3` が効かないため（ADR 0003 に明記）、
`{ window: 10, allowed: 0, maxPenalty: 2 }` で頭打ちだけを見るテストを1本立てた。

### `src/data/` の値は1つも焼き込んでいない

`BASE_HANDS` すら import していない。**`startGame` 直後の `playerHandTable` が
素の `BASE_HANDS` に等しい**ことを使って基準表を取り、そこからの差分だけを見る。
`desperateBonus` も `currentEnemy(state).desperateBonus` から期待値を作っている。
`/balance` でどの数値を動かしても、この2ファイルは壊れない。
