# ADR 0003: 連打の罰を「熱」から「直近4手の窓」に変える

- ステータス: **確定**
- 決定日: 2026-08-10
- 前提: `docs/adr/0001-battle-model.md`（**覆さない**）、`docs/adr/0002-hand-heat.md`（**一部を覆す。下記**）

## 背景

ADR 0002 は「同じ手の連打を罰する」ために熱を入れた。実装後にプレイして
「**熱がたまりまくって実質二択になる。最良の手が『熱がないもの』になっている**」
という指摘が出たので、実測した。**指摘は正しく、しかも式から必然だった。**

### 1. 熱は構造的に減らない

熱は毎ターン**各手から1ずつ**冷めて、出した手に**4**たまる。手は3種類しかないので、
盤面全体では毎ターン `+4 − 3 = +1`。**増える力が減る力より強いので、頭打ちしない。**

| ターン | 熱の合計 | 1手あたり |
| --- | --- | --- |
| 2 | 7.0 | 2.3 |
| 6 | 15.3 | 5.1（弱化1段） |
| 12 | 24.1 | 8.0（弱化2段） |
| 20 | 34.2 | 11.4（弱化2段） |

109,684回の選択場面で、**2手以上が弱化している場面が 60.2%**、3手とも弱化が 16.0%、
弱化ゼロは 8.0% しかなかった。

### 2. 罰しているのは「連打」ではなく「使うこと」

ADR 0002 の本文は「同じ手の連打を罰する」と書いているが、
**実装に「連打」という条件はどこにも無い。** 手を出せば必ず +4 され、
**1回使っただけで次のターンは -1** になる。「連打かどうか」は
たまる速さと冷める速さの差に間接的にしか現れていない。

**均等に3手を回しても罰が付く**（各手は平均3ターンに1回出るが、
4ターンに1回より速いので積み上がる）。これは狙いではなかった。

### 3. ただし熱が判断を潰していたわけではない

念のため、判断の中身も測った。**ある手が他の手に全軸で勝っているなら他方を選ぶ理由はない**、
という支配関係で「実質の選択肢の数」を数えた（重み付けをしないので評価関数の主観が入らない）。
軸は「即時のHP収支／にらみの蓄積／外したときの痛さ／熱のコスト」の4つ。

- 選択肢が2つ以上ある場面: **95.4%**
- 決め手になった軸: にらみ **54.0%** / HP収支 40.3% / リスク 26.8% / **熱 24.1%**

**熱は決め手として最も弱い軸だった。** 体感とのズレは、
**画面が熱しか語っていない**ことによる（熱だけが `-1` と明示され、
にらみの得も外したときの痛さもボタンに出ていなかった）。
これは表示の問題として別に対処する（`docs/03` 節7）。

## 決定

### 1. 罰の条件を「直近N手の使用回数」にする

```
直近 window 手（今回の手を含む）で、その手を c 回出していたとき
    弱化 = min(maxPenalty, max(0, c − allowed))
    ダメージからこの値を引く。ダメージは最低 1 で止まる

window = 4、allowed = 2
```

**溜まる／冷めるという状態を持たない。** 直近の履歴だけを見る。

| 出し方 | 弱化 |
| --- | --- |
| 均等に回す（グチパグチパ） | **なし** |
| 2連続を挟む（グググチパ ではなく ググチパ） | **なし** |
| 3連続 | -1 |
| 同じ手だけ | -1 → **-2 で頭打ち** |

**「均等回しと2連続は罰なし、3連続から罰」がこの決定の狙い。**
避けたいのは「同じ手だけを出す」という戦略性のない状態であって、2連続ではない。

> **`maxPenalty` は現状の `window`／`allowed` では効かない**（最大 c = 4 なので弱化は 2 まで）。
> 窓を広げたときに深くなりすぎないための蓋として残してある。

**ルールは敵にも同じように適用する**（ADR 0001・0002 の原則を維持）。
敵の手の抽選は重み付きのままで、履歴には反応しない。

### 2. 手の値を改定する

熱を外すと**パーが一強**になった（使用率 53.5%）ので、あわせて改定する。**構造は変えない。**

| 手 | ADR 0002 | 本ADR | 変更点 |
| --- | --- | --- | --- |
| グー | 3ダメージ ＋ にらみ×**3** | 3ダメージ ＋ にらみ×**4** | 溜めの報酬を上げる |
| チョキ | 5ダメージ | 5ダメージ | **変更なし** |
| パー | **4**ダメージ ＋ 3回復 | **3**ダメージ ＋ 3回復 | 打点を下げる |

**パーは回復ではなく打点を下げた。** 回復を下げると器用貧乏になり、
「削られてから効く手」という役割がぼやける。打点を下げるほうが役割がはっきりする。

そして `docs/01_requirements.md` の「**回復量は与えたダメージ − 1 を超えない**」により、
**打点を下げると回復も自動的に下がる**（3ダメージなら回復は 2 で頭打ち）。
実測でも「3ダメージ+回復3」と「3ダメージ+回復2」は完全に同じ結果になった。

**それでも回復は 3 のまま残す。** 強化で打点が 4 になったとき、
**そのとき初めて回復3が出せる**ようになるため。強化に意味が生まれる。

| パーの強化 | 打点 | 実際の回復 |
| --- | --- | --- |
| なし | 3 | 2 |
| +1 | 4 | **3** |
| +2 | 5 | 3 |

### 3. 強化の行き先を手ごとに変える

**グーの強化は基礎ダメージではなく、にらみ倍率に乗せる。**

| 手 | 強化1回につき |
| --- | --- |
| グー | にらみ倍率 +1（×4 → ×5 → ×6） |
| チョキ | ダメージ +1 |
| パー | ダメージ +1（＝回復の解禁） |

**3手の強化がそれぞれ別の意味を持つ**ようになる。
そして**にらみはあいこを狙う読みでしか溜まらない**ので、
**グーの強化はまともに読んだプレイヤーにしか還元されない。**
実測でも、これだけで機械的パターンの最良が 12.0% → 9.9% に落ちた。

> **`domain` に「グーはにらみが伸びる」と直書きしない。**
> 強化の行き先は `src/data/hands.ts` の `UPGRADE_TARGETS` から渡す
> （`CLAUDE.md` のレイヤ規約。`/balance` で行き先そのものを動かせる）。

`docs/01_requirements.md` の「+1 は必ずダメージ側に乗る」は
**回復側に乗せると終了保証が壊れる**ことが理由だった。にらみ倍率は純粋な加算ダメージで、
回復にも耐性にも関わらないため、この理由は当たらない。

### 4. 本気モードで敵の攻撃力を上げる

**敵のHPが半分以下になったとき、敵の全手のダメージに `desperateBonus` を足す。**

これまで本気モードは「手の傾向が変わる」だけで、危険になった実感が薄かった。
フェーズの切り替え条件は**増やさない**（`docs/01_requirements.md` の「条件は1つだけ」を維持）。
画面には既に「本気」バッジと被弾ダメージが出ているので、**強化は数字でそのまま伝わる。**

## 効果（実測・20,000周）

| 指標 | ADR 0002（熱） | 本ADR |
| --- | --- | --- |
| 通しクリア率 | 32.8% | **33.5%** |
| 1戦の平均ターン | 12.2 | **13.0**（要件 10〜14） |
| 手の使用分布 | 22.5 / 36.5 / **41.0** | **29.8 / 38.7 / 31.5** |
| 最良の機械パターン | 7.3% | 9.9% |
| 貪欲プレイとの差 | +25.5pt | **+23.6pt** |
| **均等回しで罰が付くか** | **付く** | **付かない** |
| **2連続で罰が付くか** | **付く** | **付かない** |

**3手の使用率が揃った**ことが最大の成果。ADR 0002 の時点では
パーが 41% で頭一つ抜けていたが、31.5 / 38.7 / 29.8 まで均された。

### 譲った点

**機械的パターンの最良が 7.3% → 9.9% に上がった。** 思考停止プレイがわずかに通りやすい。
ただし貪欲プレイ 33.5% との差は **+23.6pt** あり、
ADR 0002 が掲げた「機械的パターンが最適でなくなった」という基準は保たれている。

**3手が均等に使われる状態と引き換えなら妥当**と判断した。

### 数値の信頼度

ADR 0002 と同じく、**機械的パターンの勝率は評価関数に依存しない実測値**だが、
**貪欲プレイ側は自作のヒューリスティックで打った参考値**であり、真の最適とは限らない。
「+23.6pt 強い」ではなく「**機械的パターンが最適ではない**」ことの証拠として読む。

計測は `scripts/measure.ts`。数値を触るたびに回す。

## ADR 0002 のどこを覆し、どこを維持するか

### 覆すもの: 「履歴キュー方式」の却下

ADR 0002 は却下表にこう書いていた。

> **履歴キュー方式**（直近N手の出現数で減衰）— 効果はほぼ同等（+17.0pt vs 熱方式 +16.1pt）だが、
> 直近6手のキューを両陣営ぶん持つ必要があり状態が大きい

**却下理由は「効果が劣る」ではなく「状態が大きい」だけだった。**
本ADRは **N = 4** で足りるので、状態は「3手ぶんの履歴 × 2陣営」であり、
熱方式の `Record<Hand, number>` 2つと大差ない。**却下の前提が成り立たない。**

そして ADR 0002 執筆時には**熱方式が構造的に増え続けることが分かっていなかった**。
これが新しい証拠である。

### 覆さないもの

- ADR 0001 の戦闘方式（グー/チョキ/パー・にらみ・上限2・あいこダメージ）
- **同じ手の連打を罰するという方針そのもの**（本ADRはそれを**より正確に**実装する）
- **ルールは敵にも同じように適用する**
- **敵に履歴学習AIを作らない**（敵の抽選は重み付きのまま。窓は威力にしか効かない）
- 却下済みの案（累積型・連続型・PP・リキャスト・追加行動・溜めゲージ）はそのまま却下

### 名前について

内部名は `heat`／「熱」のまま残す（改名の costs が 3日の規模に見合わない）。
ただし**「溜まって冷める」という説明はもう正しくない**ので、
`docs/03` の記述は「直近4手で3回以上出したら弱化」に統一する。
**画面の表示は `-N 熱` ではなく `連打 -N` にする**（何が起きているかをそのまま書く）。

## 影響

- `src/domain/handTable.ts` — `HeatCounts` を `readonly Hand[]`（直近の履歴）に。
  `HeatRule` を `{ window, allowed, maxPenalty }` に。`heatPenalty` の引数が変わる
- `src/domain/handTable.ts` — `buildHandTableWith(base, counts, targets)` を追加
- `src/domain/enemy.ts` — `EnemyDef` に `desperateBonus`
- `src/application/game.ts` — 敵の手の表を組み立てる箇所を1つにまとめ、
  本気の強化をそこで掛ける（`ctx` と `enemyForecast` がずれないようにする）
- `src/data/hands.ts` — 値の改定と `UPGRADE_TARGETS`
- `src/data/heat.ts` / `src/data/enemies.ts` / `src/data/player.ts` — 数値
- `src/ui/` — 表示を「連打 -N」に
- `src/domain/battle.ts` / `BattleState` — **変更なし**
- 乱数の使用箇所は敵の手決定の1箇所のまま

### バランスの数値は決定ではない

採用時点の実測値は次のとおりだが、**これらは `/balance` で動かす前提**であり、
本ADRが縛るのは**構造**（窓方式・強化の行き先・本気強化の有無）だけ。

| | 値 |
| --- | --- |
| `HEAT_RULE` | `{ window: 4, allowed: 2, maxPenalty: 3 }` |
| `BASE_HANDS` | グー `{3, 0, 4}` / チョキ `{5, 0, 0}` / パー `{3, 3, 0}` |
| `UPGRADE_TARGETS` | グー `stareBonus` / チョキ・パー `damage` |
| 敵HP | 18 / 21 / 21 / 24 / 26 |
| `desperateBonus` | 全敵 1 |
| `PLAYER_MAX_HP` | 25 |

## 積み残し

- **機械パターンの最良（パー/グー交互）が 9.9%。** ADR 0002 時点の 7.3% より通りやすい。
  気になるなら `/balance` で敵の偏りを調整する余地がある
- **本気強化は全敵一律 +1。** ボスだけ +2 にするなど、敵ごとに差をつける余地がある
  （`src/data/enemies.ts` だけで動かせる）
- **`maxPenalty` が現状の窓では効かない。** 窓を広げるときに意味を持つ
