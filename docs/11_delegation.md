# 委譲（サブエージェント・Codex）

> `CLAUDE.md` から切り出したもの。**他のモデルに何かを渡そうと考えたとき、渡す前に読む。**
> ここを読まずに渡すと、範囲を切らずに渡す・テストを緑にするだけの修正を招く、といった
> 過去に一度潰した失敗を繰り返す。

## 分担の軸は1つ

サブエージェントは**空のコンテキストで起動する**。会話の経緯を引き継げないため、
「ここまでの流れを踏まえた判断」には向かない。**独立して検証できる仕事にだけ使う。**
迷ったら使わず、自分でやること。

**残っている仕事が「読むこと」か「決めること」か。**

読む・展開する・検査する作業は委譲できる。**決める作業は委譲できない。**
迷ったら「これは読めば分かることか、決めなければならないことか」を自問する。

判断が要らないものは、さらに手前で**スクリプトに落とせないか**を考える（`scripts/check-layers.sh`）。
スクリプトで済むならトークンは 0 になる。

| 工程 | 安いモデルに出す部分 | Opus が持つ部分 |
| --- | --- | --- |
| 調査 `/research` | 案の洗い出し — `battle-research` (sonnet) | 実装コストの検証、ユーザーへの提示 |
| 要件定義 `/spec` | 抜け漏れの検査 — `spec-review` (haiku) | **案の選択、ADR、「やらないこと」の線引き** |
| 基本・詳細設計 `/design` | **なし（出さない）** | **全部** |
| テスト作成 `/test` | テストの記述 — `test-designer` (sonnet) | 期待値の根拠が設計にあるかの確認 |
| 実装 `/impl` | 実装 — **Codex (gpt-5.6-luna)** | 差分の確認、**エラー時の切り分け** |
| レビュー `/conform` | 適合検査 — `design-conformance` (haiku) | 指摘の採否 |
| 素材 `/assets` | 発注仕様 — `asset-brief` (sonnet) | 点数を絞る判断 |
| バランス `/balance` | 数値の書き換え — Codex (luna) | 何が問題かの言語化、プレイしての確認 |
| 行き詰まったとき | `codex-rescue` (Codex) | 別系統のモデルの視点 |

### 設計だけ委譲しないのは意図的

`/design` は手戻りが最も高く、かつ **`/test` と `/impl` がこの精度に依存している**。
ここが曖昧なまま下流に流れると、曖昧さが増幅されて返ってくる。
浮かせたトークンは手戻り1回で吹き飛ぶ。

### メインで行うもの

- **要件定義・設計** — 対話を引き継げないサブエージェントには渡せない
- **小さな修正** — コールドスタート（CLAUDE.md と docs の読み直し）のほうが高い
- **Codex の差分の確認** — `npm run check` が通っても設計と違うことはある

### 報告を鵜呑みにしない

サブエージェントの指摘は自分でコードを読んで裏を取ってから採否を決める。
**sonnet は実装コストを楽観的に見積もる傾向がある**ので、調査結果の「3日で作れる」は自分で検証する。
数式・期待値の類は**自分で解き直す**（`docs/00_research.md` 節6.5 は実際にそれで誤りを見つけた例）。

## 失敗したときの担当

判断の軸は「どちらのモデルが安いか」ではない。
**残っている仕事が「読むこと」か「決めること」か。** 読むことは委譲できる。決めることはできない。

### 第1段階 — 失敗が原因箇所を示しているか

| 失敗の出かた | 対応 |
| --- | --- |
| 型エラー・レイヤ規約違反（ファイルと行が出る） | **luna に直接差し戻す。Opus は介在しない** |
| 例外・スタックトレースが実装を指している | **luna に直接差し戻す。Opus は介在しない** |
| アサーション失敗（期待値と実測値だけ） | Opus が失敗を読む → 第2段階へ |
| ハング・タイムアウト | Opus が失敗を読む → 第2段階へ |

### 第2段階 — 残っている仕事は何か

| 状態 | 担当 | なぜ |
| --- | --- | --- |
| **原因も直し方も分かった** | **Opus が直す** | 残りは1〜数行の編集。渡すと codex 一往復と差分レビューが乗り、確実に高くつく |
| **見当はつくが、確定にはコードを読む必要がある** | **luna に渡す** | その読む作業が luna の文脈で起きることが委譲の価値。ここが本来の使いどころ |
| **見当もつかない** | **`docs/03` を疑う** | 実装ではなく設計の穴の可能性。コードを読み進める前にここを確認する |

どちらでも2回外れたら、そこで初めて Opus が腰を据えて診断する。
原因が設計側にあるとき、Codex は何度やっても同じ壁に当たるため。

## Codex に渡すとき

### 渡す前に必ずコミットする

`codex exec` はワークツリーを直接書き換える。渡す前にコミットしておけば、
`git diff` が Codex の変更そのものになり、まずければ `git checkout .` で戻せる。

規約は `AGENTS.md` が持っているので、**プロンプトに規約を書き写さない。**
設計のどの部分を実装するのかだけを指定する。

```bash
codex exec --model gpt-5.6-luna --full-auto "<設計のどの部分を実装するか>" < /dev/null
```

**`< /dev/null` は必須。** 付けないと Codex が stdin からの追加入力を待って止まる。

### 「範囲」と「あるべき挙動」を両方書く

アサーション失敗を「このファイルを直して通せ」とだけ渡すと、
luna は**テストを緑にすること自体を目的にできてしまう。**

```ts
if (hp < 0) hp = 1;   // テストは通る。挙動は間違い
```

**テストが通る間違った修正は、遅い修正より悪い。** 製品に残り、しかもテストが
もう守ってくれない。これを防ぐため、渡すときは必ず次の2つを書く。

1. **触れてよいファイル**（1つに絞る）— 範囲を切らないと別の層を壊す
2. **あるべき挙動**（`docs/03` の該当箇所を引く）— 通し方を縛らないと手段を選ばなくなる

```bash
codex exec --model gpt-5.6-luna --full-auto "tests/scenario/battle.test.ts が失敗している。
src/domain/battle.ts だけを修正する。docs/03 の通り HP は 0 未満にならないこと。
テストと他のファイルは変更しない。" < /dev/null
```

渡す前にコミットしてあれば、外れても `git checkout .` で無料で戻せる。
ただし**「戻せるから雑に渡してよい」ではない。** 戻すこと自体は無料でも、
外れた往復のトークンは戻らない。

### hook は Codex の書き込みには効かない

hook は Claude の Edit / Write ツールに紐づいている。`codex exec` は別プロセスとして
ファイルを直接書くため、**hook は発火しない。**

したがって Codex から戻ってきたら、**必ず手動で回す。**

```bash
git diff --stat && npm run check && git diff tests/
```

自動化に頼れない唯一の箇所なので、手順として固定する。

## 検査はまずスクリプトで

`scripts/check-layers.sh` で判定できる規約違反に、モデルのトークンを使わない。
新しい規約を足すときは、**まず grep で書けないかを検討する**。書けるならスクリプトに追加し、
`design-conformance` には書かない。
