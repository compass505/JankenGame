# 進め方（工程・コミット・テスト・素材）

> `CLAUDE.md` から切り出したもの。**工程に入るとき、コミットするとき、テストを書くときに読む。**
> CLAUDE.md には常時必要な規約だけを残し、手順の詳細はここに置く。

## 工程

**3日で作り切る規模**。この順に進め、飛ばさない。

```
/research → /spec → /design → /test → /impl → /conform → /balance
  調査      要件定義   設計    テスト作成  実装    適合確認   調整
```

| | 工程 | 成果物 |
| --- | --- | --- |
| 0日目 | ハーネス整備 | **完了済み** |
| 1日目 | 調査 → 要件定義 → 基本設計 | `docs/00〜02`, ADR |
| 2日目 | 詳細設計 → テスト作成 → 実装 | `docs/03`, `tests/`, `src/` |
| 3日目 | 適合確認 → バランス調整 | `src/data/` |

### 3日で目指さないもの

**バランスの完璧さは目標ではない。** ユーザーの方針として、動くものを3日で作り、
バランスは後日ゆっくり良くしていく。だから数値は `src/data/` に集約してある。
3日目に調整が終わらなくても、それは失敗ではない。

削る判断に迷ったら、**バランスの作り込みから削る。** 遊べる状態まで到達することを優先する。

## コミットと push

**コミットのタイミングは Claude が判断してよい**（ユーザーから委任済み）。
コミットしたら**毎回 push する**。手元にだけ溜めない。

| タイミング | 例 |
| --- | --- |
| 工程の成果物が固まったとき | 調査完了、要件確定、設計完了 |
| モジュール1つが動いてテストも通ったとき | `domain/janken.ts` + そのテスト |
| **Codex に渡す直前** | 差分を切り分けるため（`docs/11_delegation.md`） |

**`npm run check` が通らない状態でコミットしない。** 壊れた状態はセーブポイントにならない。

### 唯一の例外: `/test` 直後の1コミット

`/test` は実装より先にテストを書く工程なので、**モジュールが存在せず `npm run check` は必ず落ちる。**
これは壊れた状態ではなく、**この工程の正しい成果物**。次の2つの理由からコミットする。

1. `/impl` で Codex に渡す前にコミットしておかないと、`git diff` が
   「Codex が書いたもの」にならない（`docs/11_delegation.md`）
2. テストが先にコミットされていることが、**実装がテストに合わせた証拠**になる

**このコミットだけは、失敗の中身が「実装がまだ無い」ことだけを指していると確認してから行う。**
該当するのは次の2つで、**それ以外のエラーが混ざっていたらテスト側の不備**なので先に直す。

| コード | 意味 | いつ出るか |
| --- | --- | --- |
| `TS2307` | モジュールが無い | 新しいファイルを作る機能 |
| `TS2305` | モジュールにその export が無い | **既存モジュールへの追加**（熱のような後付けの機能） |
| `TS2339` | 型にそのプロパティが無い | 既存の interface へのフィールド追加（`GameState.playerHeat` 等） |
| `TS2353` | 知らないプロパティを渡している | 同上を**オブジェクトリテラル側**から見たとき（`EnemyDef.desperateBonus` 等） |
| `TS2724` | その名前の export は無い（似た名前はある） | **関数の改名**（`buildHandTable` → `buildHandTableWith`） |
| `TS2554` | 引数の数が合わない | **シグネチャの変更**（`heatPenalty` が2引数から3引数へ） |
| `TS2739` `TS2488` | 型の形が違う／反復できない | **既存の型の作り替え**（`HeatCounts` が `Record` から配列へ） |

**上の3つだけで済むのは「足すだけ」の変更のとき。**
ADR 0003 のように**既存の型やシグネチャを作り替える**変更では、下の4つも必ず出る。
コードの種類ではなく、**すべてのエラーが `tests/` にしか出ていないこと**で判定するほうが確実。

```bash
npx tsc --noEmit 2>&1 | grep '^src/' || echo "エラーは tests/ だけ = 正しい状態"
```

`src/` は改訂前の設計のまま一貫しているので**この時点では緑**であり、
`src/` にエラーが出ていたら、それは未実装ではなく**実装か設計の側の壊れ**である。
そのうえで、失敗しているテストの一覧が**その工程で足した設計の項目と一致する**ことを目で確認する。

`/impl` が終わった時点で `npm run check` は必ず緑に戻す。**赤のまま次の工程に進まない。**

リポジトリは **Public**（https://github.com/compass505/JankenGame）で、**人に見せる目的で公開している。**
README とコミットメッセージは他人が読む前提で書く。

### GitHub Pages

実装が動いてから設定する。今はデプロイするものがないので不要。
**2日目に実装が動いた段階で、ユーザーに提案すること。** 遊べるURLがあると人に見せやすい。

## テストの3層

実行はどの層もスクリプトで、トークンは 0。モデルが出てくるのは**失敗したあと**だけ。

| 層 | 置き場所 | 検証するもの | 実行 |
| --- | --- | --- | --- |
| ユニット | `tests/unit/` | `domain/` の純粋関数 | vitest |
| **シナリオ（結合の本体）** | `tests/scenario/` | `domain` + `application` を通した1試合 | vitest |
| ブラウザ確認 | なし（手動） | UI を含めた画面遷移・表示・操作 | 開発サーバ |

**結合テストの本体は `tests/scenario/`。** UI を含まないので自動化でき、シードを固定すれば
決定的に回る。ここに投資するのが最も安い。ブラウザでしか確認できないものだけを手動に回す。

詳細な方針（シナリオは3本まで、途中の数値を検証しない、UIはテストしない）は
`docs/04_test-plan.md` にある。

### テストは実装より先に、別のモデルで書く

実装と同じモデルにテストを書かせると、テストは「仕様通りか」ではなく
「実装した通りか」を検証してしまい、バグを追認する。

`/test` → `/impl` の順を崩さない。先にテストがあることで、Codex の仕事が
「既にあるテストを通す」という機械的な作業になり、成功率も上がる。
**Codex がテストを書き換えていないかは毎回 `git diff tests/` で確認する。**

## ブラウザでの確認

表示や操作の確認は、開発サーバを起動して**自分で確認する。ユーザーに確認を代行させない。**
`npm run check` が通っても、表示崩れ・操作感・面白さは保証されない。

これは現状メイン（Opus）が担当する。スクリーンショットを扱うためメイン文脈を最も消費するが、
画面数が少ないうちは分離のコールドスタートが上回る。
**スクリーンショットが嵩んできたら、表示崩れの検出だけをサブエージェントに分ける**ことを検討する
（「面白いか」は判断なので分けられない）。

## 画像素材

画像は imagegen で生成する。**Claude 側では生成できない。**

1. `docs/05_assets.md` に発注仕様（ファイル名・サイズ・プロンプト）を用意する
2. ユーザーに提示する。ユーザーが Codex 経由で imagegen に依頼して画像を作る
3. ユーザーが `public/assets/` に指定のファイル名で置く
4. Claude 側で読み込んで表示を確認する

**素材待ちで実装を止めない。** CSS の図形や絵文字でプレースホルダを置き、
後から差し替えられる形で先に組み上げる。ファイル名は仕様書で確定したものを使い、後から変えない。

## 作業のしかた

- `.ts` を Edit / Write すると hook が型チェック・関連テスト・レイヤ規約を自動実行する。
  失敗したら**その場で直す**。次の作業に進まない。
- テストは `tests/unit/` に純粋ロジック、`tests/scenario/` に1試合の再現テストを置く。
- 数値のバランス調整は `src/data/` の中だけで完結させる。ロジック側に定数を散らさない。
